## 一、拆分设计的综合框架（统领全文）

> **核心认知：拆分不是"能跑就行 vs 必须拆"二选一，是综合权衡多个维度后的工程判断。没有"默认动作"——每个场景都独立分析。**

### 拆分依据：多维度综合权衡

判断一个加工要不要拆成多步，看这几个维度：

| 维度 | 含义 | 倾向拆 | 倾向合 |
|------|------|--------|--------|
| **正确性** | 拆不拆都不能错（永远最高优先级） | — | — |
| **性能** | 单步跑不跑得动 | JOIN 重/聚合重/数据量大 | 单步轻量 |
| **可维护性** | 职责单一好改好测 | 多职责纠缠、独立可检查 | 单一职责已清晰 |
| **存储** | 中间表占空间 | — | 中间表大且只用一次 |
| **扩展友好** | 加来源/加字段方不方便 | 多来源、业务在演进 | 单一稳定来源 |

### 设计取向：倾向扩展友好

> **不管未来变不变，扩展友好的设计本身是合理的。** 这不是"猜未来会变"，是一个工程取向——
> 多来源拆成各自独立规则、职责单一便于增改，这种设计即使当下够用也是更好的。
>
> 但它是一个**倾向性权重**，不是"必须拆"。当下条件明确不支持拆（如单来源简单加工）就不拆。

### designer 的决策方式

- **自主决策，少弹问人**：基于当下能掌握的信息（加工结构、JOIN 数、复用性、数据量档位）综合分析，给出判断
- **不套默认**：每个场景独立分析，不因"看起来像某场景"就直接套结论
- **在 design_approach 说明理由**：为什么这样拆/不拆，让闸口①人能看懂你的思考

### 决策时的优先级

正确性 > 性能 > 可维护性 > 扩展友好 > 存储

- 永远先保证正确（拆不拆都不能错）
- 性能不达标必须拆（单步跑不动没商量）
- 在性能达标的前提下，倾向可维护+扩展友好的拆法
- 存储是最后的反作用力（只在中间表大且只用一次时才压"合"）

## 二、复杂度信号（性能+可维护性维度的具体判据）

> 这些信号帮你判断"单步是否复杂到该拆"。**信号衡量的是结构特征，不是表面数量**——
> 5个同质聚合字段不算复杂（天然一组），5个异质聚合才算；3层简单桥接链不算复杂，3层实质加工才算。

### 真复杂度信号（命中任一 → 考虑拆）

| 信号 | 判定依据 | 为什么是真复杂度 |
|------|---------|----------------|
| **JOIN 表数 > 12** | 数物理 JOIN 的表 | 不管简单复杂，12 张表 JOIN 单条 SQL 难写对、优化器也吃力 |
| **异质聚合共存** | 一个规则里多种不同 GROUP BY 逻辑的字段（GROUP BY 键不一致） | 不同聚合维度纠缠，改一处影响别处；该按聚合维度拆 |
| **聚合后关联** | 先 GROUP BY 再 JOIN | 两阶段逻辑，优化器行估算易偏 |
| **关联链上有实质加工** | 中间层不只是桥接（多对多关联无计算），而是每层都有独立 JOIN+计算 | 每层是独立逻辑单元，该各自成步 |
| **CTE/子查询依赖链 ≥3 层** | a→b→c→d，每层依赖前一层（不是多个独立 CTE 扁平拼合） | 深度依赖链改一层影响后面所有层；提成 CTE 改善可读性但改不了依赖深度 |

### 不是复杂度信号（旧版误判，已删）

- ~~聚合字段≥5~~：5 个字段按同一 GROUP BY 聚合是天然一组，不拆。改用"异质聚合共存"判定
- ~~关联链≥3 层~~：简单桥接（多对多中间表无计算）层数多也不复杂。改用"关联链上有实质加工"判定
- ~~嵌套子查询>4 层~~：嵌套可提成 CTE 变扁平，层数是写法特征不是逻辑复杂度。改用"依赖链深度"判定

### 信号判定的关键细节

**异质聚合 vs 同质聚合**：
```
同质（不拆）：5个字段都按 GROUP BY user_id 聚合 → 一次 GROUP BY 搞定，天然一组
异质（该拆）：3个字段按 user_id 聚合 + 2个字段按 product_id 聚合
             → 不同维度，拆成两个 aggregate 步骤各自 GROUP BY
```

**CTE 依赖链 vs 扁平 CTE**：
```
扁平CTE（不拆）：WITH user_dim, prod_dim, order_fact AS (...) 
                最后扁平 JOIN → 各CTE独立可懂，不复杂
依赖链（该拆）：WITH a, b依赖a, c依赖b, d依赖c → 深度链，提成CTE也还是4层依赖
               拆成物理表才能打断依赖、各自独立检查
```

## 三、CTE vs 物化决策（决定拆了之后用什么承载）

> 业界共识（Brent Ozar + Microsoft Azure SQL）：**默认从 CTE 开始，命中条件才物化成物理中间表**。

### 决策维度

| 判断维度 | CTE 够用 | 必须物化物理中间表 |
|---------|---------|-------------------|
| 中间结果引用次数 | 只用一次 | **多次引用**（重算浪费）|
| 行估算准确性 | 优化器估算准 | **估算偏差 >10x**（误差放大致性能崩）|
| 数据量 | 小 | **大**（需索引加速 JOIN）|
| 可调试性 | 不需检查中间数据 | **需要检查点**（排查问题）|
| 跨步骤传递 | 单条 SQL 内 | **跨步骤**（多 rule 数据流）|

满足任一"必须物化"条件 → 建物理中间表。否则用 CTE 内联。

> 真实案例：CTE 重的过程 90 分钟 → 改成索引临时表后 15 秒（差 360 倍）。
> 多步骤 ETL 天然适合物理中间表——每步产出可检查、可复用、可索引。

### 数据量因子（★ 尽力而为）

数据量大（亿级）会显著放大 JOIN 重分布成本，倾向物化。但数据量是**尽力而为的输入**：

- RS 的 data_exploration 段可能有，也可能没有
- designer 能用 explore.py 查开发环境，但和生产不一致——**只能判档位（万/百万/亿），绝对值不可信**
- 拿得到 → 填 `complexity_analysis.data_volume` 档位，作为物化决策的加权因子
- 拿不到 → 标"未知"，走复杂度信号判断（不阻断）

数据量只影响"物化 vs CTE"这一个决策点，不影响分布键选择（分布键看主键/关联频率/离散度，与数据量无关）。

## 四、案例分析（展示"怎么综合分析"，不是给模板套）

> 这些案例展示的是**分析方法**——把当下条件列全、综合权衡、给出结论和理由。
> 不是让你"遇到 union 就这么干"。每个场景独立分析。

### 案例A：多维度 JOIN（含事实表聚合）

```
场景：订单宽表，要补这些属性：
  - 用户维度（简单维表 LEFT JOIN，取 user_name/user_level）
  - 商品维度（简单维表 LEFT JOIN，取 product_name）
  - 用户消费总额（需聚合订单事实表：SUM(amt) GROUP BY user_id）
  - 商品销量排名（需聚合订单事实表 + 排名：ROW_NUMBER OVER(... ORDER BY SUM DESC)）
```

**当下条件分析**：
- 加工复杂度：2 个简单维表 JOIN + 2 个复杂聚合（消费总额/销量排名）
- JOIN 表数：4（订单+用户维+商品维+订单事实聚合），未到 12 阈值
- 异质聚合：是（消费总额按 user_id 聚合，销量排名按 product_id 聚合）
- 复用性：消费总额和销量排名各自独立，无交叉
- 数据量：订单事实表可能大（聚合成本高）

**综合判断**：把 2 个复杂聚合各拆成独立 aggregate 步骤，2 个简单维表 JOIN 留在装配步
- R0001：aggregate → tmp_user_amt（用户消费总额）
- R0002：aggregate → tmp_prod_rank（商品销量排名）
- R0003：full 装配 → 目标表（JOIN tmp_user_amt + tmp_prod_rank + 用户维 + 商品维）
- **理由**：两个聚合是异质的（不同 GROUP BY 键）、各自复杂（一个 SUM 一个 ROW_NUMBER）、且订单事实表大（聚合成本高，独立物化可加索引加速）。简单维表 JOIN 不拆（同质——都是"补属性"这一职责）

**反向条件**：
- 如果用户消费总额只是简单 SUM（无排名逻辑）且数据量小 → 可以 CTE 内联，不单独物化
- 如果只有 1 个聚合维度（不是 2 个）→ 不拆，CTE + JOIN 一步到位

### 案例B：多来源 union（你提的真实场景）

```
场景：订单数据从两个系统来（A系统+B系统），字段大部分重叠
  A 需要：简单字段映射
  B 需要：补两个计算字段（金额×汇率、状态码映射）
  目标：合并到一张宽表
```

**当下条件分析**：
- 加工复杂度：A 简单映射，B 中等（2 个计算字段），都不复杂
- JOIN 数：0（纯 union，无性能压力）
- 复用性：无（只进一个目标表）
- 数据量：单来源量级中等
- 来源数：2 个

**综合判断**：拆成各自独立规则，写同一临时表（分区隔离来源），再装配到目标
- R0001：source_a → tmp（分区=source_a），A 的字段映射
- R0002：source_b → tmp（分区=source_b，build_mode=accumulate），B 的计算字段
- R0003：tmp → 目标表
- **理由**：扩展友好（未来加 C 来源 = 加 R0004 规则，不动 A/B）；各自加工独立可检查；写同一临时表（分区隔离）存储代价可控
- 这不是"猜未来会加来源"，是"扩展友好的设计本身合理"

**反向条件**：
- 如果两来源加工都极简单（纯映射无计算），且确认是稳定单一来源不会扩展 → 可以一个规则 UNION ALL（少调度步骤）
- 如果两来源数据量都极大，合一起 UNION 也跑不动 → 拆是性能强制

### 案例C：增量取数与加工分离

```
场景：增量资产，A表（主表，按 update_time 增量）+ B表（从表，提供金额字段，按 dt 增量）
  目标行 = A JOIN B，任一表变化都要重建
  加工涉及：JOIN B 取金额 + JOIN 用户维表取用户名 + 2个计算字段
```

**当下条件分析**：
- 增量范围：A、B 都是驱动表，变化都要抓（并集影响范围，见 incremental-playbook 模式三）
- 加工复杂度：中等（JOIN 维表 + 2 个计算字段）
- JOIN 表数：3（A+B+用户维），未到阈值
- 职责：取增量范围 / 加工字段 / 写入目标，三个职责

**综合判断**：拆三步（取数/加工/写目标）
- R0001：取 A+B 的增量并集范围 → tmp（incremental_extract 或 full+WHERE OR）
- R0002：读 tmp，JOIN 维表 + 计算字段 → tmp_processed（aggregate 或 full intermediate）
- R0003：tmp_processed → 目标表（merge 或 full）
- **理由**：三个职责独立变化（增量字段可能改、加工逻辑可能改、写入策略可能改）；拆开后改一处不影响别的；中间产物可独立检查（增量范围对不对、加工算得对不对）

**反向条件**：
- 如果加工极简单（无 JOIN 维表、无计算字段）→ 取数+加工合并一步（两步）
- 如果是单驱动表（无并集问题）→ 取数+加工合并，merge 单独（两步）

### 案例D：头行整合 + 维度补充

```
场景：订单头表（一行=一单）+ 订单明细表（一行=一商品行）
  目标：一行=一单（头表粒度），但要补明细聚合字段（商品数、总金额）
  还要 JOIN 用户维、商品维
```

**当下条件分析**：
- 粒度变化：明细（行级）→ 头（单级），需先聚合明细
- 加工复杂度：明细聚合（COUNT/SUM GROUP BY 订单号）+ 维度 JOIN
- 异质聚合：否（明细聚合是单一 GROUP BY 订单号）
- JOIN 表数：头表+明细+用户维+商品维 = 4

**综合判断**：聚合用 CTE 内联，不拆物理中间表；维度 JOIN 也不拆（简单属性补充）
- 一个 full 规则：CTE 先聚合明细 → JOIN 头表 → JOIN 维度 → 目标
- **理由**：明细聚合是同质的（单一 GROUP BY）、数据量未大到要物化、维度 JOIN 是简单属性补充（同职责）。CTE 内联可读性够用，拆物理表反而碎
- 如果是 assemble_ts 多步骤——仍可一个 full 规则（CTE 内联），不必拆

**反向条件**：
- 如果明细聚合本身很复杂（多层嵌套 + 关联其他事实表）→ 拆 aggregate 步骤
- 如果明细数据量极大（聚合跑不动）→ 物化中间表加索引

## 五、step_type 决策（拆分定了之后，step_type 是结构映射）

### ★ 关键认知：中间表 ≠ 聚合

"中间表"（target_role=intermediate）按"产出供谁消费"定义，跟聚合无关：
- 聚合产出中间表 → `aggregate`（intermediate）
- **非聚合的加工步骤产出中间表** → `full`（intermediate）← 合法！为了可读性分步加工，不一定要聚合
- 增量取数到中间表 → `incremental_extract`（intermediate）
- 单步聚合直灌目标表 → `aggregate`（target）← 合法！一步聚合搞定不必拆

### 决策顺序

```
该规则是否处理增量数据？
├─ 否（全量）
│   ├─ 产出中间表（供下游消费）？
│   │   ├─ 含聚合 → aggregate（intermediate）
│   │   └─ 纯加工分步（可读性拆分）→ full（intermediate）★ 允许
│   ├─ 直灌目标表？
│   │   ├─ 含聚合 → aggregate（target）★ 允许（单步聚合直灌）
│   │   └─ 简单直取/装配 → full（target）
│   └─ 读中间表装配目标？→ full（target，reads=[中间表]）
└─ 是（增量，详见 incremental-playbook）
    ├─ 从源表取增量到临时表？→ incremental_extract（intermediate）
    └─ 合并临时表到目标？     → merge（target，reads=[临时表]）
```

### 四种 step_type

| step_type | 用途 | target_role 可选值 | 什么时候选 |
|-----------|------|-------------------|----------|
| `full` | 单规则直灌目标（CTE 内联）；读中间表装配目标；非聚合的中间加工步骤 | target / intermediate | 简单场景、最终装配、可读性分步 |
| `aggregate` | 聚合产出（中间表或目标表） | intermediate / target | 异质聚合拆步；单步聚合直灌 |
| `incremental_extract` | 从源表取增量到临时表 | intermediate | 增量：每张驱动表一个 |
| `merge` | 合并临时表/中间表到目标 | target | 增量合并 |

> assemble_ts 只校验**结构上不可能对**的组合：intermediate+merge（中间表不会是合并步骤）、target+incremental_extract（目标表不会是取数到 tmp）。其余组合都合法。

### target_role

- `intermediate`：中间表（每次重建用完即丢）
- `target`：目标 F 表（按 load_mode 管理）

### produces_for / reads（与 data_flow.dependencies 互补）

- `produces_for`：中间表规则填，产出供哪些规则消费（rule_code 列表）
- `reads`：装配/merge 规则填，读哪些中间表（表名列表）
- **自引用例外**：reads 含自己 target_table 时（累积共建场景），不参与循环检查

## 六、螺旋式中间表设计

中间表设计是螺旋的——先骨架后回填：

1. **先骨架**：复杂度评估后决定建几个中间表，定表名/粒度/用途
2. **字段逻辑**：确定每个字段加工逻辑时，识别哪些字段落在中间表
3. **回填字段**：从字段分配回填出每个中间表的完整字段清单（在 field_targets 里列出）

中间表的字段绝大多数与目标表字段同名同类型（透传/聚合），极少量 designer 自建字段（辅助计算中间产物）。中间表统一加审计字段（脚本自动处理）。

### 中间表的产出模式

中间表（target_role=intermediate）有两种产出方式，靠 `build_mode` 声明：
- `transform`（默认）：单一规则一次性产出
- `accumulate`：多规则累积共建（去重累积 / union 累积）

详细场景和排重策略见 **incremental-playbook §三/§四**。本 playbook 聚焦复杂度判断，累积共建的数据流细节在那里。
