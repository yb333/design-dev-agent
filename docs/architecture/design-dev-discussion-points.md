# 设计开发 Agent：讨论论点记录

> 本文档记录我们在设计 PPT 过程中，通过深入讨论得出的核心论点和判断。
> 这些论点不是"已确定的方案"，而是**经过推理和辩论后达成的共识**——后续落地设计将基于这些论点展开。
>
> 版本：v0.1 · 2026-07

---

## 论点 1：IT设计和开发是一体的，不拆开

### 论点
IT设计（产出 TS）和开发（编码）在同一个 agent 里连续完成，中间不拆断、不交接。但内部层次清晰。

### 推理过程
- **初始判断**：IT设计和开发吃同一个上下文（技术 spec），是 AI 在生成代码的不同阶段
- **质疑**：细设计已经把每个字段的加工逻辑写出来了，那后面的开发是不是就很简单了？那设计开发还需要一体吗？
- **最终结论：还是要一体**，理由三个：
  1. **细设计和编码的边界在实战中是模糊的**——想清楚加工逻辑的那一刻，SQL 表达式就出来了，不会先写伪代码再翻译
  2. **分开了上下文就断了**——agent 从粗TS到细TS到SQL是一个连续的思维过程，交接=信息丢失
  3. **返工时一体最快**——编码时发现细设计有问题，agent 直接回改，不用反馈给另一个段

### 准确表述
> "设计开发一体" = 一个 agent 连续完成"粗设计→细设计→编码→UT"，中间不拆断、不交接。但内部层次清晰：粗TS、细TS是设计（产出 spec），编码是开发（产出代码），两者性质不同。

## 论点 2：TS 应该分粗和细两层

### 论点
现在的 TS 是粗的——只说"步骤有几个、每个步骤干什么"。真正的设计应该分成粗 TS 和细 TS 两层。

### 结构
```
RS（需求spec）
  ↓ IT设计（核心）
粗 TS：步骤划分 + 每步大致干什么 + 场景识别 + 表级血缘
  ↓ 闸口①（人确认方向）
细 TS：每个步骤里每个字段怎么加工、转换规则、CASE分支
  ↓ 编码（基础）
DDL + ETL 代码
```

### 为什么"细设计"是核心
- "每个字段在每个步骤里怎么加工"——这才是真正的智能判断
- 粗 TS 只是搭骨架（分几段），细 TS 才是填血肉（每个字段的表达式、转换逻辑、CASE WHEN 分支）
- **从粗到细这一步，才是设计判断最密集的地方**

### 为什么现在编码显得不简单
因为细设计这层缺失了，智能判断被挤进了编码阶段。**补上细设计，编码就真的变回基础了。**

---

## 论点 3：闸口①在粗设计之后、细设计之前

### 论点
第一道闸口应该在粗设计之后、细设计之前——先确认方向，再往里填细节。

### 理由
1. **粗设计是"方向决策"**——如果方向错了（分段策略错了、场景划错了），细设计做得再好也白费
2. **细设计如果方向没确认就做，改起来代价大**——每个字段的转换逻辑都要重新想
3. **人在粗设计这个闸口，判断的是"方向"**——这是人最该拍的事。到了细设计（每个字段怎么加工），更多是技术执行，人不太可能逐字段审核

### 细设计不需要独立的闸口
细设计没有独立产出物给人审，它融在代码里。它的正确性由"闸口②审代码 + UT 跑数据"来兜底。

---

## 论点 4：细设计和编码在实际落地时是一体的——不先写文档再出代码

### 论点
拿到确认后的粗设计后，不会先写一份细设计文档，再基于文档出代码。而是"边想边写"——细设计和编码是同一次思考的两个面。

### 实际执行过程
1. **逐步骤展开**：一个步骤一个步骤地处理
2. **每个步骤内，逐字段想加工逻辑→直接写SQL**：想清楚一个字段的加工逻辑，SQL 表达式同时就写出来了
3. **写SQL时同时套规范**：业务逻辑（`amount * rate`）和规范（`COALESCE(amount*rate, 0)`）在同一个思考里同时处理
4. **全写完后，细TS作为投影提取**：从代码反向提取细TS（每字段：源→表达式→转换类型）

### 为什么不先写文档
人脑（和AI）想业务逻辑的方式，就是直接想成表达式，不是先想成中文再翻译。先写文档再翻译，是给两种不同的人/系统协作时才需要的。

### 细TS的性质
细 TS 不是前置 spec（先写再做），而是**投影 spec（做完再提取）**。它的用途：
- 给人看（不用读SQL就能理解字段加工逻辑）
- 给下游用（测试、影响分析读这份spec）
- 给优化场景用（代码理解Agent反向工程产出的就是这个）

### 与"生产SQL是唯一真相源"的关系
完全一致——**代码是真相，细TS是真相的投影**。

## 论点 5：规范是编码的事，不是细设计的事

### 论点
细设计想的是"业务逻辑该怎么加工"（无规范约束），编码想的是"怎么把加工逻辑写成符合规范的SQL"（受规范约束）。

### 分界线
| | 细设计（想逻辑）| 编码（写代码）|
|---|---|---|
| 关心什么 | 字段怎么算、过滤什么、关联谁 | SQL语法对不对、规范合不合规 |
| 受规范约束 | **不受**——纯业务逻辑 | **受**——DDL要IF NOT EXISTS、ETL不能SELECT *、NULL要COALESCE |
| 出错会怎样 | 业务逻辑错（算错了）| 规范不合规（被lint打回）|

### 这解释了编码为什么不是纯机械
编码 = 把细设计的业务逻辑，套上平台规范和SQL语法，翻译成可执行代码。
- 不机械在"翻译"（翻译本身简单）
- 不简单在"要同时满足一堆规范约束"
- 但规范是确定的、有标准答案的 → 可以被静态自检自动验证

### 分工
- **细设计**：想业务逻辑（核心智能，无规范约束）
- **编码**：把逻辑套上规范写成SQL（规范性实现，被规范约束）
- **静态自检**：检查规范合不合规（确定性验证）

## 论点 6：编码是"基础"不是"核心"——准确定义

### 论点
编码归类为"基础（规范性实现）"，不是核心壁垒。

### 为什么是基础
不是因为它简单，而是因为**它被 TS 和规范约束住了——判断空间不大**：
- TS 已经把"怎么分段、字段怎么映射、血缘怎么走"都定了
- 编码是在这个框架内"填实现"
- 真正难的判断在 IT设计（产出 TS）那一步，不在编码

### 如果被质疑"编码怎么会是机械的"
完整回答：
> "编码要同时满足很多规范，确实不简单。但规范是确定的、有标准答案的——关键的业务判断在细设计那步已经做完了。编码是把业务逻辑套上规范写成SQL，所以是规范性实现，不是核心智能。"

### "基础"的准确含义
不是"没技术含量"，而是**"规范性实现——判断空间被 TS 和规范锁死了"**。

## 论点 7：spec 为源是分层的——前置 vs 投影

### 论点
真正的"spec为源"是分层的，不是所有 spec 都是前置的：

| | 前置spec（先写再做）| 投影spec（做完再提取）|
|---|---|---|
| 粗 TS | ✅ 前置——必须先确认方向再往下 | — |
| 细 TS | ❌ 不会前置写 | ✅ 投影——从代码提取 |
| RS | ✅ 前置——BA先产出 | — |

### 核心
- **粗层（RS、粗TS）**：前置 spec，人确认后才往下走
- **细层（细TS）**：代码是源，细TS是代码的投影

代码本身就是最精确的 spec，细 TS 只不过把代码里隐含的加工逻辑，提取成人/机器可读的结构化形式。

## 论点 8：四件套交付物

### 论点
设计开发段的交付物是四件套，不是抽象的"三类"：

| 制品 | 是什么 | 给谁 | 特点 |
|---|---|---|---|
| **DDL** | 建表语句 | 自行部署到环境 | 单独制品，DDL和ETL绑定生成 |
| **术加（ETL制品）** | ETL代码打包成术加平台格式 | 执行平台 | 术加只管ETL运行+捞日志 |
| **LTS（调度制品）** | 调度配置 | 调度平台 | 开发段产出配置 |
| **DQ（质量检查制品）** | 质量检查SQL及制品 | 后续管 | 只产出不管运行（无开发环境），涉及SQL开发 |

### 关键点
- ETL 不是裸代码交付，是打包成术加制品
- DDL 是单独制品（不是术加管的）
- 术加只管 ETL 运行和日志回传，不管建表/查结构（那是开发环境数据库的活）
- DQ 只产出制品，不在开发段运行

## 论点 9：平台协同——读连接，制品推到各平台开发环境

### 论点
每个平台是制品的目的地。读用 MCP 连，制品推到对应平台的开发环境。

### 平台与制品的对应关系
| 平台 | 制品去向 | 开发段做什么 |
|---|---|---|
| 开发环境数据库 | DDL制品→建表 | 查结构/验证类型/建表 |
| 术加（执行平台）| 术加制品→运行ETL→捞日志 | 部署ETL制品，拿日志判断成功没 |
| 调度（LTS）| LTS制品→配置调度 | 开发段做调度配置 |
| DQ（质量检查）| DQ制品→只产出 | 不管运行（无开发环境）|
| 元数据/血缘 | — | 读（查已有血缘·待评估）|
| 云链（需求）| — | 关联：制品与需求记录 |

### 三条红线
1. **语义判断不自主**——数据合理性、模式选择、字段语义 → 给材料，人定
2. **推到生产不自主**——写生产库、推规则上线、发布 → 生成制品，人推。推到开发环境是正常的
3. **重写不自主**——优化推倒重来 → 只精确修改，想重写走新建

## 论点 10：代码稳定 vs 数据准确——两层分开

### 论点
Agent 的结束点 = 代码在开发环境稳定 + 数据已摆给人。

### 两层拆分
| 层 | 谁判 | 停止条件 | 性质 |
|---|---|---|---|
| 代码稳定（技术层）| **Agent** | 建表成功、ETL跑通、无报错、机械校验过 | 可自动判定，agent 能喊停 |
| 数据准确（语义层）| **人** | 业务方确认"数据符合业务预期" | 不可自动判定，人喊停 |

### "数据准确"永远不归 agent
不是 agent 能力不足，是这些事本来就该人定（业务判断）。把它明确交给人，agent 反而清清楚楚。

---

## 论点 11：螺旋回路——与开发环境咬着转

### 论点
不是"造完交付走"，是螺旋迭代：改→部署开发环境→跑→捞结果→改，直到稳定。

### 三个接点（打通了回路自动转）
1. **部署**：代码→开发环境（agent 直推）
2. **捞结果**：跑完→捞执行结果/日志（agent 自动读）
3. **判断**：错误信息→怎么改（agent 读报错→定位→改）

### Agent 边界
Agent 是"造车的工厂"，不是"开车的车队"。但交付前要螺旋到开发环境稳定——不是造完就走。

### 判断边界的简单标准
> "这是在造代码，还是在代码造完之后的事？" 造代码→agent管；造完之后→下游段。

## 论点 12：新建 vs 优化——一个 agent，两个入口

### 论点
新建和优化不需要拆成两套系统。差异只在"进入IT设计前怎么拿到 spec"，进入后完全合流。

### 两种入口
- **新建**：设计开发 agent 吃 1 个输入（RS），从零生成
- **优化**：设计开发 agent 吃 2 个输入——变更 RS（增量·只描述要改什么）+ 现状 spec（代码理解 Agent 产·含改动边界）

### RS 和现状 spec 的关系
**并行产出、串行合并**——两个独立 agent 并行产出，设计开发 agent 等两个都到位后合并。

### 优化铁律
生产 SQL 是唯一真相源，旧 TS 只是随动描述（生产代码可能已被手工改过，与设计文档脱节）。

---

## 论点 13：代码理解是独立 Agent，不是设计开发的内部 skill

### 论点
代码理解应该独立成 agent，不绑在设计开发流程里。

### 三个理由
1. **产出是对外契约，不是内部数据**——现状 spec 要被多方消费（设计开发/运维/影响分析/文档）
2. **生命周期不同步**——设计开发是一次性的，代码理解是被反复调用的
3. **对接的平台不同**——设计开发碰开发环境数据库，代码理解要读生产代码（可能从执行平台/元数据/调度拉）

### 当前状态
代码理解能力当前内嵌在 analyzer skill 里，尚未独立化。

---

## 论点 14：端到端是多个专业 Agent 靠 spec 交接

### 论点
不同的职责段由不同的专业 agent 承担，它们靠 spec 交接，谁也不碰谁的内部。

### 架构
```
需求 Agent → [RS] → 设计开发 Agent → [TS+制品] → 测试 Agent → ... → 运维 Agent
                                    ↑
                        代码理解 Agent → [现状spec]
```

### 核心理念
spec 不光是人和 agent 之间的语言，也是 agent 和 agent 之间的语言。RS、现状 spec、TS 三者结构必须对齐——这是架构级要求。

### 下游
设计开发 agent 的下游是**测试 Agent**（不是运维）。运维是上线后更下游。

## 论点 15：能力矩阵——核心/基础/增强三层定位

### 论点
设计开发 agent 的所有能力分三层定位。没有附属——每一项都有明确战略归属。

### 分类原则
- **核心壁垒**：必须守住，别人替代不了（投入大、价值高）
- **基础（规范性实现）**：判断空间被 TS 和规范锁定，量大但非壁垒
- **增强**：提升上限，当前缺的要补

### 核心能力清单
1. spec 协议规范（RS/粗TS/细TS 结构定义+对齐）——整个体系的地基
2. 新建场景编排（9阶段状态机）——agent 的灵魂
3. 优化场景编排（反向→精确修改）——与新建共享主干
4. 粗设计（RS→粗TS）——骨架方向决策
5. 细设计+编码（一体）——业务逻辑核心智能
6. 代码理解（输入能力·独立Agent）——壁垒

### 战略叙事
> "核心在编排·协议·设计（粗+细）·代码理解——编码和格式转换是基础，不是壁垒。"
