八个步骤一条龙：AI 干活，程序把关，人只在两处拍板

从输入校验到制品落档案，每一步都有明确的责任者——人只在闸口①②出手，其余时间全程自动，且每一步的产物都落盘可查。

★ 新建交付（本讲主线）

  • 适用：全新目标表，从零到档案一次跑完
  • 输入：RS + mapping 两个文件，路径发起即可
  • 产出：设计文档 + 四件套 + UT 报告 + 平台制品包
  • 周期：流程连续跑完，人只需在两处确认

  • 全量 mapping 上标注变更行（版本+动词），RS 附变更记录
  • 只做精确增量：新增字段/逻辑，存量零接触，双向比对冻结列
  • 设计原则与质检机制和新建完全一致，信任同一套护栏

03 · 设计原理 Ⅰ

三条红线：自主权收窄到「干活」，判断权留给人

这不是能力限制，是刻意的设计决定——全自动交付省下的是人力，赌上的是数据正确性：错一次，就是无声上线的脏数据。

1 语义判断不自主

业务含义永远由人定

  • 关联键怎么收敛、表的粒度是什么、主键是哪几个——这些只有懂业务的人能判断
  • 智能体的做法：拿证据来问——类型风险、值域溢出、关联键对账，全部整理成选择题
  • 实例：实测发现某关联键不唯一时，它报告差异证据、给出收敛选项，选哪个由你定

2 推生产不自主

上生产永远是人按按钮

  • 全部产物只落到档案目录，不触碰生产环境
  • UT 通过 ≠ 自动上线：闸口②确认后制品入档案，推不推、何时推，人来定
  • 它是「交付到门口」，不是「送进家门」

3 重写不自主

存量只做精确修改

  • 已有资产的变更，只做声明的增量改动，绝不推倒重来
  • 改了什么、没改什么，双向比对出报告，冻结列零差异可验证
  • 「AI 把我的存量改乱了」这件事在机制上不会发生
一句话：它负责把活干完并自证质量；语义你定、生产你推、存量它不碰。这三条写在流程机制里，不是提示词里的承诺。

04 · 设计原理 Ⅱ

AI 干活，程序质检：它说「通过」，是有证据的通过

生成者不负责证明自己对——质检全部由确定性脚本完成（不跑大模型，同样输入必得同样结论），证据全部落盘可回溯。

确定性质检（每一步都有）

  • 结构校验 ~40 条：设计文档一落盘就查——引用存在性、增量闭合、口径可解析、别名冲突……不合规直接拦截并指出层级
  • 连库查证：字段存在性、类型对账、值域探测——读真实数据库，不靠猜
  • UT 真实执行：INSERT 跑真库 + 主键/空值/行数实锤 + 执行计划门槛，报告留档
  • DQ 实跑：违规行探测器——0 行通过，非 0 行告警并带样例数据
  • 闸口材料 = 脚本产出：你在闸口看到的摘要和实测结果，是确定性脚本从产物里抽的，不是 AI 转述

失败分流：UT 失败 ≠ 都丢回程序员

  • SQL 语法错 → 恢复编码会话修复，每规则限 3 轮
  • 数据质量问题（主键重复/空值/行数异常）→ 绝不给编码 先跑关联诊断定位，带着证据退回设计层
  • DQ 告警 → 人判三选：SQL 方向反→改码 / 阈值不合理→改口径 / 数据真脏→修源
  • 环境问题 → 停下报告修复指引，不重试不绕过
  • 每轮修复的诊断证据都落盘（_internal/diagnose/），改了什么、为什么改，全部有据可查
为什么数据问题绝不给编码 agent？真实教训：编码 agent 遇到「主键重复」，会顺手用 ROW_NUMBER 去重「修好」——表面通过，实际关联发散的根因被掩盖，数据悄悄变少。根因在设计层，所以数据问题永远带着证据退设计、回闸口①复审。

07 · 使用方式 Ⅰ

你要准备什么：两个文件，职责分明

mapping 管字段映射（体积的 90%），RS 管元数据——都有模板，照着填即可；输入写得越清楚，预检阶段拦下的问题越多。

文件你提供什么模板
mapping
90% 体积		 源表清单（实体级）、字段映射全量（源/目标字段名+类型+中文名）、加工逻辑（人话即可，如「按合同+pu 汇总发票金额，排除非洲发票」）、目标表中文名 mapping模板.xlsx——一行一映射，列头即格式
RS
元数据		 目标表 schema.table、调度方案/频率/SLA、增量识别方式+驱动表+增量字段、初始化时间范围、DQ 规则（有需求就写，没有就没有，不强行凑）、数据量级/空值率 RS模板.md——分节填空，L1.1/L06/L07 对号入座

没有 RS 也能跑

  • mapping 独立驱动核心链路，调度/增量/DQ 用默认兜底（全量调度、T+1、无 DQ）
  • 但信息不全，90% 场景建议带上 RS——调度、增量、DQ 的设计质量直接受益
  • RS 里最容易漏的三样：增量驱动表、初始化时间范围、调度 SLA——漏了它会在闸口来问

输入铁律：声明宁缺勿错

  • 它按声明执行——关联条件声明错了，就错着执行；不确定的条件宁可先不写，问到了再补
  • 映射逻辑拿不准的写「需业务确认」，它会带着问题到闸口来找你，而不是自己编
  • 字段名/类型写错不用怕：预检连库对账，这一步就拦住，进不了设计

08 · 使用方式 Ⅱ

流程中你做什么、怎么发起：全是选择题，不给开放题

人的每次出手都被设计成有材料的快速拍板——证据、选项、后果摆在一起，选一个就行。

你的出手清单

  • 预检提问（类型/值域/关联键）：如类型风险三选一——直接复制 / 加安全处理（截取降级）/ 不处理；值域溢出——源端改模型 / 拍板取舍
  • 闸口①：看设计摘要 + 关联质量实测结果，回答「方向对不对」
  • 闸口②：看 UT 报告 + DQ 告警样例，确认质量；告警三选——SQL 方向反→改码 / 阈值不合理→改口径 / 数据真脏→修源
  • 每次提问都附证据与后果说明；不答流程就停在这里，没有秘密默认值

发起与恢复

  • 手工发起：/new-pipe + 模式与文件路径（模式：新建 / 优化）
  • 总控对接：Task 直连编排 agent，参数 = 模式 + 两个文件路径，其余可选
  • 中断恢复：问题（如源数据修复）处理后凭 task id 续命，从断点继续，不从头重跑
  • 无人值守：non-interactive 模式——闸口不等待、产物留人后审；但人工决策类问题仍会停下问（无安全默认，不代答）
内部回路不需要你盯：SQL 修复自动闭环（每规则限 3 轮）、数据问题自动带证据退设计、环境问题停下报告——只有需要「人的判断」的事才会来找你。

09 · 注意事项

边界与预期：它强在哪，不承诺什么

把边界说在前面，用起来才不会失望——它把「做」的活干完并自证质量，「判」的权始终在你。

它不做什么

  • 不替你定业务语义：粒度、主键、关联收敛——材料给你，你拍板
  • 不推生产：制品到档案为止，上线动作永远是人的
  • 不重写存量：只精确修改，改了什么可验证

输入决定输出

  • 声明条件宁缺勿错——它按声明执行，声明错就错着执行
  • RS 元数据段（调度/增量/驱动表）要准，这层错会直接进设计
  • 源表数据脏是失败的最大概率归宿：正确反应是修输入重跑，不是让它改 SQL 掩盖

诚实披露

  • UT 零告警 = 当前数据上通过，≠ 阈值永远合理——数据分布变了告警口径可能要调
  • 优化场景存量语义不补（主键/粒度留空走豁免，双跑兜底）
  • 环境有前提：目标库连库配置就绪；部署环境不向流程暴露无关的数据库连接（避免它连错库得出错误结论）
期望管理一句话：它是「证据充分的助手」，不是「免责的黑盒」——每个结论都能翻到落盘的证据，每个判断点都留在你手里。
