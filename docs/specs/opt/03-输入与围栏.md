# 03 · 优化输入与变更围栏

> ⚠️ v3 修订（2026-08-21，真实输入格式确认）：§一的输入形态已按真实格式重定义——变更标识从专用列改为 **mapping 备注列 `{YYYYMM}版本{动词}` 标记**（专用列规格废弃）；**delta mapping 取消**（未来只交全量 mapping + RS），delta↔full 对账线删除，漏标防线改为闸口①'简述↔字段并排人扫；版本锚点 = RS 变更记录最新"优化"行日期归一 YYYYMM；其他动词（修改/下线）识别归类报告"待扩展"而非拒收。实现见 preprocess_opt v2（--input-dir 分拣 + manifest）。§二起的两级声明/围栏/审计机制不变。

> 第3章定稿。核心结论：输入通道唯一 + 显式标识权威；两级声明模型；审计机制 = 冻结层/自由层模型（声明驱动的比对引擎）；人机审查分工按原则9（审查收敛）。

---

## 一、输入形态（✅ 定稿）

- **输入通道唯一**：RS + mapping（带显式变更标识）。触发源头（业务主动 / 源端变更倒逼 / 巡检发现）**不是本体系的关心属性**——所有需求一律按本格式进来，不存在第二种输入格式（原"源端驱动"议题撤销）。
- **mapping 为业务侧交付物（v2.2 修正，对齐 02/01）**：我方只发布输入格式规格（`docs/specs/mapping-format.md` 扩展"变更标识"枚举列），与交付方对齐；业务侧怎么产出（基于逆向视图加工 / 手写 / 自建资产用建表时的原 mapping）不是我们的事，**不做跨 agent 设计**。
- **显式标识为权威**：mapping 新增结构化"变更标识"列（实体级 / 属性级各一，枚举值——机器可靠，输入方可能是 agent，颜色/批注不可用）。第一刀只认"新增"，其他值报"本刀不支持的变更类型"。
- **交叉校验（diff 辅助）**：标"新增"但 baseline 已有 → 冲突报告；未标但 baseline 没有 → 提示漏标问人；旧 mapping 对照出的漂移 → 报告。
- **RS 优化章节**：新字段业务口径、回刷意向、DQ 需求（完全跟随输入原则，无系统兜底）。

## 二、两级声明模型（✅ 定稿）

| 层级 | 产出者 | 内容 | 职责边界 |
|------|--------|------|---------|
| 业务级 `change_request.json` | preprocess 优化版（落 `_internal/`） | 业务说了什么：字段、含义、源意图、口径/回刷意向 | **不含落位信息**——在哪改/怎么改/改成啥样不是输入的事 |
| 设计级 `ts.change` 段 | designer（闸口①'人确认） | 落位：挂哪条规则、JOIN/血缘怎么走、中间表加不加列 | 是设计判断，不是逆向事实也不是需求内容 |

- 围栏许可 = 两级合体。
- **change_request ↔ ts.change 对账**：不夹带（设计多于业务）、不漏接（业务多于设计）。

## 三、审计机制：冻结层/自由层模型（✅ 定稿；第一刀只实现 add_field 矩阵）

**定义**：每份变更声明自带"冻结/自由矩阵"——冻结层（逐项等价比对，用稳定键）、自由层（放开）、枚举许可（新增清单）。**比对粒度跟着冻结层走，不跟规则走**。机制正名"声明驱动的比对引擎"（fence_check），"围栏"是 add_field 场景的直觉叫法。

**三段审计链**：
1. 意图→落位：change_request ↔ ts.change 对账；
2. 落位→结构：ts_v2 ↔ ts_baseline，冻结层比对（fence_check，designer 组装后、闸口①'前）；
3. 结构→代码：新 SQL ↔ baseline SQL，AST 级"老列投影逐字等价 + 仅追加"（归属第5章定，算法原则本章定）。

**变更类型矩阵示例**（设计压力测试，证明模型可表达；第一刀仅实现第一行）：

| 变更类型 | 冻结层 | 自由层 | 枚举许可 |
|---------|--------|--------|---------|
| add_field | 一切（字段集除新增/存量血缘/存量SQL/规则结构） | — | 新增字段清单 |
| add_source | 字段集、未声明影响字段的表达式、规则结构 | 声明影响集内字段的表达式 | 新来源（表+JOIN） |
| 性能重构 | 对外可观察层：目标表结构、端到端血缘（目标字段→物理源）、调度语义 | 内部结构：规则划分/中间表/SQL 写法 | — |
| modify_field | 除声明字段外的一切 | 声明字段的表达式 | — |

- **判定标准**：文本/AST 级不等价就拦，不看语义等价；等价改写必须先声明再改。笨标准换可审计。
- **因果锚**：自由层/许可项可加"变化必须可归因于声明原因"的 AST 检查（如 add_source 的新表达式必须引用新来源）——声明不是橡皮图章。
- **大变更场景裁判移交**：重构类"外部=目标表结构+数据"，结构等价围栏审，数据等价双跑审；双跑 oracle 本身由声明参数化（影响集外逐值不变、影响集内符合声明）。

## 四、人机审查分工（✅ 定稿，即原则9）

- 机器审计（冻结层+双跑）是**独立防线**：人全点通过也拦得住越界。
- 人审项只收机器判不了的语义判断，呈现为**具体可回答的问题**，不给全量 diff 墙；防确认疲劳是闸口设计硬约束。
- 矩阵每格标注"机器审 or 人审"：add_field 接近全机器审；refactor 类机器守外壳+人审内部合理性。

## 五、双跑定位（✅ 收敛）

- 双跑 = **开发环境验证机制**：新老 SELECT **同数据同时点**比对（实现见第6章：双向 MINUS 检查项），oracle 按声明参数化。（v2.2 修正：原"固定输入快照"表述废弃。）
- 生产影子表 / 灰度 = **需求层面内容**（RS 声明），agent 不决策不实现；闸口只呈现相关事实（如开发库数据代表性的限制声明）。
- 语义层无机器标准，数据等价是代理指标（第6章细化执行机制）。

## 六、围栏外变化的处置（✅ 定稿）

1. **designer 越界**（改了未声明的存量）→ 硬阻断，报错带 `[围栏]` 导航（对齐 assemble_ts 风格），指引两条路：撤回，或走清单扩充；
2. **变更清单可扩充，必经人**：designer 发现存量问题想顺手修 → 提议 → 闸口①'呈现【建议追加的变更】→ 人确认 → change_request 更新 → 回 designer（与 new-pipe 6b"人定方案后才回 designer"同构）；
3. **输入自带越界**（标识出现第一刀不认的类型）→ 报告人：改回输入，或本次升级为多类型优化（第一刀拒收，明说）。
4. **漏改**：枚举许可每条必须在 diff 中有落点，没有 = 硬阻断（"恰好等于"的双向性）。

## 七、围栏围不住的（诚实边界）

1. 行为层（AI 乱执行 DDL / 临时脚本）→ 权限与流程；
2. 时间窗外漂移（逆向后线上被别人改）→ 交付前漂移复检（第7章）；
3. 语义位（`_unknown`，无原值可围）→ 数据等价作代理（双跑）；
4. 数据层后果 → 双跑。

## 挂账

- fence_check 归属已定（独立脚本，不塞 assemble_ts）；SQL 级比对的工具归属 → 第5章。
- baseline mapping 生成器 → 第2章（组装器职责之一）。
- 闸口①'/②'的人审项清单（按原则9收敛后的具体问题列表）→ 第4/6/7章各自定义。
