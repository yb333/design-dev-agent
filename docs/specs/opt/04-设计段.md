# 04 · 设计段（优化模式）

> 第4章定稿（v1.7）。designer 在优化场景的载体、输入输出形态、决策知识与闸口。前置：baseline = 档案当前态（02），change_request 已就绪（03）。

---

## 一、skill 拆分形态

```
skills/dws-design-opt/
└── SKILL.md     # 薄，单线五步：
                 # 1. 读 baseline_view（老资产长啥样）+ change_request（这次要加什么）
                 # 2. 落位决策：挂哪条规则 / 血缘怎么走 / 中间表要不要加列（知识在 opt-playbook）
                 # 3. 新 JOIN 才声明关联安全性（老 JOIN 不声明——生产在跑即证明）
                 # 4. 回刷判断（§四决策表）
                 # 5. 写增量 decisions → assemble_ts 组装 ts_v2 → 交 pipe 跑围栏
```

- **references / scripts 不搬家**：路径引用 dws-design 的知识（design-guide / incremental-playbook / complexity-playbook）与工具（explore 试算新 JOIN 唯一性、assemble_ts）。新增 `opt-playbook.md`（落位取舍树 + 回刷决策树）住 dws-design-opt。
- **agents/dws-designer.md 只加一个 skill 指针**（dws-design + dws-design-opt）。岗位、权限、角色认知零改动——"设计判断者，只改设计不改 SQL"的身份在两种模式下不变。coder 侧对称拆 dws-coding-opt（第5章）。
- **拆分判据（尺子）**：互斥（一次会话只处其一）/ 叙述重叠低（重叠的是知识不是流程）/ 演化节奏不同（优化高频迭代、新建已稳定）→ 拆 skill；反之（如无RS模式）→ 单 skill 内条件化。
- **模式显式声明**：opt-pipe 的 Task prompt 写明优化模式及输入路径，designer 不靠猜。

## 二、designer 只写增量 decisions

- **增量格式**：每个新增字段一条（挂哪条规则 / 血缘 / 新 JOIN 及其 safety / 回刷意向），存量一概不写——重写存量 decisions = 重写存量设计，红线禁止且无法审查。
- **组装**：assemble_ts 拿"ts_baseline + 增量 decisions"合成 **ts_v2 = 完整结构 + 顶层 change 段**：
  - ts_v2 本体是完整 ts——下游切片 / UT / 制品工具**零改造**即可用；
  - change 段（change type 枚举，第一刀只有 add_field）记录本次变更声明，围栏 / 闸口 / 制品 patch 消费它。

## 三、落位决策（知识进 opt-playbook）

核心判断一个：新字段从源头到目标表走哪条路——直挂目标规则（新表来源则目标规则加 JOIN）/ 穿中间表（中间表加列、多规则改写）。取舍：血缘最短路径优先；中间表被共用时加列影响面大，须谨慎并在 change 段声明。

## 四、回刷决策表

| 基线类型 | 情况 | 动作 |
|---------|------|------|
| 全量（truncate/分区） | 下次调度自动补齐 | 无需回刷，闸口说明一句 |
| 增量（merge） | 历史行新列 NULL | **人选拿**（闸口①'）：不回刷（接受 NULL）/ 回刷（人给时间范围，复用 init 双管道机制产回刷脚本；自建资产的档案 init 段可直接复用） |

RS 优化章节有回刷意向则预填，无则 pending 到闸口①'。

## 五、闸口①'（人审项按原则9 收敛，只问三个具体问题）

1. **落位确认**："X 字段挂 R00xx，新 JOIN T，中间表不动/加列——确认设计方向？"（一屏摘要，非全量设计文档）；
2. **回刷选择**（增量基线才有）：不回刷 / 回刷（带范围与代价说明）；
3. **建议追加的变更**（仅当 designer 发现存量问题提议时出现）——人确认后进 change_request，回 designer 落位（与 new-pipe 6b 同构）。

不问：全量 diff、机器已审的围栏细节。交互对齐现有闸口（question；非交互须显式声明）。

## 六、校验：存量豁免、新增全审（非重构）

- assemble_ts 的 run_all_validations **规则本身一行不改**；新增可选输入 `exemptions.json`（baseline 组装时按语义空位自动生成），判定时查表：
  - 豁免按位：baseline 空的语义位（主键/粒度/关联安全），ts_v2 同位结构未变 → 继续豁免；
  - 新增位（新字段/新 JOIN/新规则）→ 全量校验（加工逻辑必写、新 JOIN safety 必声明等）。
- 机制性质：现有"软阻断 + 豁免"的自然延伸（designer 手填豁免 → 优化场景组装器自动生成豁免）。

## 七、围栏回路

- fence_check（声明驱动的比对引擎）由 **pipe 调用**（被审计者不自审）：designer 交 ts_v2 → pipe 跑围栏 → 越界/漏改 → 报错带 `[围栏]` 导航回 designer（恢复会话），每规则限 3 轮（对齐 new-pipe 6b 纪律）。

## 八、工具归属（按调用方）

| 工具 | 归属 | 说明 |
|------|------|------|
| explore / assemble_ts / fill_type_risk_decision | dws-design/scripts（**不搬家**） | 调用方仍是同一个 designer agent（双模式）；opt 的 SKILL.md 写路径引用 |
| assemble_ts_baseline / fence_check / 标注解析 preprocess 等 | design-dev-shared/scripts | 调用方是 opt-pipe（管线节点）——边界不是"新建 vs 优化 skill"，是"agent 工具 vs pipe 管线脚本" |
