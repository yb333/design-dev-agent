# 15 · 逆向能力需求：ts 草稿补全（i_view 与 DQ 明细）

> 读者：**逆向工程侧**。本文档登记两条草稿产出需求，源自优化链路内网第一案例实报（2026-11-10/11）。
> 每条给出现象、需求、验收——实现方式（从哪解析、怎么组织）由逆向侧设计。
> 契约 schema 权威在消费方（`skills/opt-pipe/schemas/ts_draft_v2.schema.json`），本轮两项契约变更
> （i_view 必填、新增 dq 段）由消费方同步 bump，彼侧 vendor 随实现同步。

---

## R1 · meta.target.i_view 必须携带（现状：空）

**现象**：内网第一案例草稿 `meta.target.i_view` 为空 → 消费侧两个 DDL 生成器（新建全量 DDL、
优化 ALTER 变更单+视图重建）都不产出 I 视图脚本——build 与 archive 两处皆无，且链路上**无任何
拦截或提示**（i_view 在契约中是可选槽位，沉默缺省合法通过）。资产是 I/F 镜像标准形态，
视图名材料在手（mapping 声明的目标表即 I 视图名，资产标识铆定 I 视图）。

**需求**：

1. 草稿 `meta.target.i_view` 携带真实视图名（`table` 必有；`schema`/`cn` 对齐 f_table 的携带粒度）。
2. 确实没有 I 视图的资产：**显式空对象**（`{"schema": "", "table": "", "cn": ""}`）——「没有」
   也是一个要显式声明的答案，不允许沉默缺省（沉默缺省与「漏解析」在消费侧不可区分）。

**验收**：含 I 视图的资产跑 facts，草稿 `i_view.table` = 真实视图名；无视图资产，`i_view` 为显式
空对象且通过契约校验（schema 已改必填——字段在、值可空）。

## R2 · 草稿携带 DQ 规则明细段（现状：解析了但被丢弃）

**现象**：`read_dq_excel`（excel 主 sheet「规则基础信息」/ 代码仓 DQ yml 双源）已完整解析存量
DQ 制品，但 `export_ts_draft` 只携带 `dq_required` 布尔计数——**规则明细在投影时被丢弃**。
消费侧（优化链路）拿不到存量 DQ 事实：字段/来源变更触发的 DQ 影响分析无输入，存量 DQ 与
本次变更的新旧对照无从做起。

**需求**：

1. 草稿新增 DQ 明细段（数组），每条规则的字段与 `read_dq_excel` 产出**同名同构、零翻译投影**：
   `rule_number / rule_name / rule_desc / check_type / alert_level / sql / target_table /
   target_schema / owner`。
2. `rule_number` = 平台规则编码，是存量 DQ 条目的**身份键**——消费侧的变更对照（重做/新增/取消）
   以它对齐，**任何情况下不允许重新编号**。
3. `sql` = 检查 SQL 全文逐字（与 query_sql 同款保真纪律）。
4. 无 DQ 制品的资产：无该段（`dq_not_detected` 披露语义不变）。

**验收**：含 DQ 制品的案例目录跑 facts——草稿 DQ 段条数 = excel 有效规则行数（有 Number 的行），
逐字段与制品内容一致；yml 源与 excel 源产出同构；无 DQ 时草稿无该段、既有披露照常。

## 附：与本轮消费侧改造的衔接

- 消费侧将把草稿 DQ 段建档为 baseline `dq.json`（平台形态），DQ 影响分析（字段/来源变更 ∩
  DQ 锚定）由此接通——**变更驱动的存量 DQ 重做评估不依赖 RS**。
- DQ 制品 patch 自动化不在本轮范围（平台编码差异待平台盘点）——本轮只打通数据链。
