# 01 · 逆向契约（baseline_v1）

> 第1章立场定稿。**正式契约文档（发 analyzer 侧实施的 schema+说明）等全部章节讨论完、整体回顾后合成**——本文记录的是我们消费侧的设计立场与依据。
> 标注约定：✅ 已定立场；⏳ 开放（依赖第7章回填）。

---

## 一、定位与前提

- **单人双仓**（design-dev-agent 与 dws-analyzer-skill 同一维护者）：防漂移不靠沟通，靠三样硬东西——契约文档唯一、JSON Schema 双端校验、fixture 锚定（双方 CI 各自跑，不跨仓 import）。
- **调用边界（v1.1 修订）：本体系不调用 analyzer 的任何脚本**。analyzer 是 peer agent（其完整工作流含 AI 增强步骤，run.py 是内部脚本层）；逆向是**输入侧的前置动作**，baseline_v1 以**文件交接**方式交付到约定路径（对齐 export xlsx ↔ 内网 skill 的既有协作模式）。我方 pipe 从契约校验开始；baseline_v1 缺失/过期时 fail loud 并给出补齐指引（对齐 NO_DB_SOURCE 模式），不代跑、不代修。资产定位（表名→代码仓/制品包）与脚本演化归 analyzer 侧，契约保护数据形状，不延伸到调用点。
- **消费方不感知输入模式**：analyzer 从 xlsx 还是代码仓解析是生产侧的事；契约只有"事实 + 显式空"。
- 契约交付物 = baseline_v1：**纯物理事实包**。ts_baseline 的组装永远在本体系内（原则2/3）。

## 二、设计立场（✅ 定稿）

1. **形态**：独立小 schema（baseline_v1），以 `--export baseline_v1` 投影产出，与 knowledge_draft 内层演化隔离。投影薄（选取+重命名+补空）。
2. **三级语义分级**：
   - 事实（必填或显式空）：SQL/配置里写着的；
   - 判定 hint（带"非权威"标注，给人看不进 ts、不参与围栏）：load_strategy、patterns；
   - 语义（永不进契约）：增量字段、驱动表、主键、粒度——人+designer 回路。
3. **SQL 逐字保真**：`query_sql` 逐字节保留，禁止美化/重排版；不可避免的变换必须写入契约文档。围栏、双跑、漂移检测三件事共同的地基。
4. **围栏锚物理事实键**：diff 基于（表.字段集合 + lineage raw_expr 原文 + query_sql 原文），不基于对方分类标签（transform_type 等枚举演化不得影响两次优化间的判定）。
5. **缺口显式化**：拿不到的事实为显式 null + 我们侧报告"无法断言"，不静默。
6. **schema 文档跟生产方走**：契约文档 + JSON Schema 放 analyzer 仓（与投影代码同步改）；本仓 vendor 一份带版本拷贝；运行时先对 `version` 字段，不支持即 fail loud。
7. **枚举映射归我方**：delete_mode→load_mode、transform_type→加工方式等映射表是我们侧的按**平台代次**（platform_generation）维护的版本化知识，契约只带逐字原始值。术加 1.0→2.0 迁移时契约事实不变，我方加一张新代次映射表即可。
   > ⚠️ v1.1 修订（见 09 §⓪）：analyzer 侧以 `write_plan.kind` 把映射**两层化**——dm→kind 归解析侧（文法语料权威，按 platform_generation 维护），kind→load_mode 归我方。原立场的动机（迁移时代次化、契约带原始值）全部保留，权责边界经实践修正。

## 三、内容清单（✅ 定稿，⏳ 两处形态待第7章）

```
baseline_v1
├─ version                      必填      契约版本（双端校验锚点）
├─ asset                        必填      schema / table / rule_group_code / rule_group_en
│                                         dialect / source_type / analysis_time
│                                         platform_generation（平台代次，枚举映射选表依据）
├─ provenance                   必填      原始源文件定位信息（原则8）——具体形态 ⏳ 待第7章
├─ rules[]                      必填      每规则：
│     rule_code / rule_name     必填      平台稳定标识
│     exec_sequence / scenario_id / is_common   必填   → 多场景分组
│     target_schema / target_table              必填
│     delete_mode / delete_condition            必填（无则空串，逐字原始值）
│     merge_on                  dm=6 必供  MERGE ON 条件（实现来源是 analyzer 的自由）
│     query_sql                 ★必填     逐字保真 SQL 原文
│     source_tables[]           必填      SQL 内物理表
│     joins[] / where_clause / group_by[]       必填（可空）结构化事实，designer 消费
│     is_view_step / exchange_source_table      可空   视图步骤 / 交换分区
├─ tables[]                     必填      SQL 涉及全部表 {schema,name}；
│                                         fields[]{name,type,comment} 可选——DDL 缺则空，
│                                         类型回填走我方 precheck 连库（第2章定）
├─ lineage[]                    必填      {rule_code, target_field, transform_type,
│                                         raw_expr 逐字, physical_sources[]{table,field}}
│                                         CTE 穿透到物理源表
├─ schedule                     可空      任务/jobs/params（含增量变量如 END_TIMES）
├─ dq_rules[]                   可空      编号/名/口径/check_type/SQL 原文
├─ load_strategy                必填      hint 级（资产级判定，非权威）
├─ patterns[]                   可空      hint 级加工模式提示，给人看
└─ warnings[]                   必填(可空数组)  逆向交叉验证差异事实
                                          （声明 vs SQL / DDL vs SQL / SQL 内在质量）
                                          ——消费方式 ⏳ 待第7章（携带本身零成本，任何政策下不亏）
```

## 四、增量还原度结论（P0 ✅ 已勘察解除）

| 增量语义位 | 可逆向性 | 来源（已验证存在于 analyzer 代码） |
|-----------|---------|----------------------------------|
| load_mode（含 merge_into） | ✅ 事实 | delete_mode 枚举 1-6，xlsx/代码仓两链都解析 |
| write_condition（MERGE ON/删除 WHERE） | ✅ 事实 | delete_condition 列 + merge_on（新增必供项） |
| 增量调度变量 | ✅ 事实 | LTS 任务 params |
| 资产级全量/增量/分区判定 | ✅ hint | detect_load_strategy |
| NOT EXISTS 自引用增量排除 | ✅ SQL 内可见 | 模式检测已有 |
| 增量字段声明 / 驱动表声明 | ❌ 语义 | 材料（where_clause 全文）交付，结论归 designer+人 |
| 历史回刷任务发现 | ❌ 现无 | 远期可选增强；第一刀人回忆 |

**结论**：原则7（回刷进第一刀）的机制依赖全部满足——增量 SQL 原文 ✅、load_mode/write_condition ✅、回刷时间范围归人。

## 五、analyzer 侧工作清单（实施等整体回顾后启动）

1. `--export baseline_v1` 投影模式 + JSON Schema + 契约文档（放 analyzer 仓）；
2. 产出交付到**约定交接路径**（由其使用者/上游编排指定；契约文档写明路径约定）；
3. `merge_on` 抽取（dm=6 时必供）；
4. 契约期望条款：baseline_v1 必须反映**线上实跑现状**（源文件与平台的一致性由交付方保证——我方默认输入准确，不做新鲜度校验）；
5. 远期可选：补数任务发现、MERGE detail 细化。

> 注（v1.5.1）：mapping 标注载体**不在本契约内**——mapping 是业务侧交付物，我方只发布输入格式规格（mapping-format.md 扩展"变更标识"列）与交付方对齐；业务侧与逆向agent 之间怎么协作（用不用其 mapping 视图）不是本契约的事，不做跨 agent 设计。

## 六、契约测试

- fixture 语料：全量两步链路 / 增量 merge（含 dm=6）/ 多场景分组 / I 视图封装——由 analyzer 侧生成，本仓 vendor 带版本拷贝；
- analyzer CI：断言 export 过 schema；本仓 CI：断言 adapter 消费 vendor fixture 成功；
- 升级流程：契约变更 → 版本 bump → 双端同步校验器与 vendor 拷贝。
