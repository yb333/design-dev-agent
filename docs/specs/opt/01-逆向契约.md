# 01 · 逆向契约（baseline_v1）

> 第1章立场定稿。**正式契约文档（发 analyzer 侧实施的 schema+说明）等全部章节讨论完、整体回顾后合成**——本文记录的是我们消费侧的设计立场与依据。
> 标注约定：✅ 已定立场；⏳ 开放（依赖第7章回填）。

---

## 一、定位与前提

- **单人双仓**（design-dev-agent 与 dws-analyzer-skill 同一维护者）：防漂移不靠沟通，靠三样硬东西——契约文档唯一、JSON Schema 双端校验、fixture 锚定（双方 CI 各自跑，不跨仓 import）。
- **调用边界（v1.1 修订）：本体系不调用 analyzer 的任何脚本**。analyzer 是 peer agent（其完整工作流含 AI 增强步骤，run.py 是内部脚本层）；逆向是**输入侧的前置动作**，baseline_v1 以**文件交接**方式交付到约定路径（对齐 export xlsx ↔ 内网 skill 的既有协作模式）。我方 pipe 从契约校验开始；baseline_v1 缺失/过期时 fail loud 并给出补齐指引（对齐 NO_DB_SOURCE 模式），不代跑、不代修。资产定位（表名→代码仓/制品包）与脚本演化归 analyzer 侧，契约保护数据形状，不延伸到调用点。
- **调用边界（v1.7 定稿，2026-10-14：engineer 直调逆向入口——无档→给目录→收产物，v1.6 的 agent 形态当天退役）**：接口收窄为两个路径（制品目录进、asset_facts.json 出）——判型/manifest/执行/失败处理全归逆向侧内部，我们不构造任何中间结构（资产标识不传，防串包由我方验收侧对账）；逆向不设 subagent 岗位（export 通道零 AI，套 agent=确定性动作包 AI 壳，纯开销）。完整需求=12 章 v3 纯需求版。仓不合并（analyzer 双使命：资产事实包给本段、spec 重建给 RS 段）不变；真第三方供方仍可走直交 json 兼容通道。
- **调用边界（v1.6，已被 v1.7 取代，留档）**：我方新增薄 agent `dws-reverser`（岗位=逆向翻译者：身份+权限+指向 analyzer skill，同 designer/coder/producer 模式），opt-pipe 步骤 0 无档分支自动 Task 起调——输入=制品文件路径清单+资产标识，输出=baseline_v1.json 落约定路径，随后走既有契约校验入料。**仓不合并**（analyzer 双使命：契约 A=baseline_v1 给本段、契约 B=spec 重建给 RS 段——多消费者能力独立保留）。**"不调 analyzer 脚本"仍成立**（起调的是 agent 不是脚本，契约仍以文件形态落盘交接）；真第三方供方出现时可退回"直交 json"旧模式（兼容保留）。翻案依据：v1.4 立法的真价值在**实现边界**（我们不碰解析语料/方言/平台代次映射），不在**谁发起调用**——防线由 schema+fixture 双端校验承担，与调用方无关；单人双仓之下"用户手工跑 analyzer+搬 json"只剩旅程摩擦（用户旅程割裂），无防线价值。
- **消费方不感知输入模式**：analyzer 从 xlsx 还是代码仓解析是生产侧的事；契约只有"事实 + 显式空"。
- 契约交付物 = baseline_v1：**纯物理事实包**。ts_baseline 的组装永远在本体系内（原则2/3）。

## 二、设计立场（✅ 定稿）

1. **形态**：独立小 schema（baseline_v1），以 `--export baseline_v1` 投影产出，与 knowledge_draft 内层演化隔离。投影薄（选取+重命名+补空）。
2. **三级语义分级**：
   - 事实（必填或显式空）：SQL/配置里写着的；
   - 判定 hint（带"非权威"标注，给人看不进 ts、不参与围栏）：load_strategy、patterns；
   - 语义（永不进契约）：增量字段、驱动表、主键、粒度——人+designer 回路。
3. **SQL 逐字保真**：`query_sql` 逐字节保留，禁止美化/重排版；不可避免的变换必须写入契约文档。围栏、双跑、漂移检测三件事共同的地基。
4. **围栏锚物理事实键**：diff 基于（表.字段集合 + lineage raw_expr 原文 + query_sql 原文），不基于对方分类标签（transform_type 等枚举演化不得影响两次优化间的判定）。
5. **缺口显式化**：拿不到的事实为显式 null + 我们侧报告"无法断言"，不静默。
6. **schema 文档跟生产方走**：契约文档 + JSON Schema 放 analyzer 仓（与投影代码同步改）；本仓 vendor 一份带版本拷贝；运行时先对 `version` 字段，不支持即 fail loud。
7. **枚举映射归我方**：delete_mode→load_mode、transform_type→加工方式等映射表是我们侧的按**平台代次**（platform_generation）维护的版本化知识，契约只带逐字原始值。术加 1.0→2.0 迁移时契约事实不变，我方加一张新代次映射表即可。
   > ⚠️ v1.1 修订（见 09 §⓪）：analyzer 侧以 `write_plan.kind` 把映射**两层化**——dm→kind 归解析侧（文法语料权威，按 platform_generation 维护），kind→load_mode 归我方。原立场的动机（迁移时代次化、契约带原始值）全部保留，权责边界经实践修正。
8. **三支柱——一次使用的支点（2026-10-14 定）**：逆向对同一资产只发生一次，由三件事支撑——**契约自足**（后续流程[组装/围栏/双跑/patch/回刷]需要的物理事实契约里全有，缺即显式 null+warnings，后续流程无任何理由回头再问逆向）/ **档案固化**（契约入档后 baseline=档案当前态，advance 推进，逆向退场；唯一重启通道=覆盖重入料[线上被外力改，人确认]）/ **交卷即终态**（逆向产物自校验全绿才交卷——同 dws-dq-producer"写完即跑修到全绿才交卷"模式）。"不反复调用"指**流程级一次**（逆向只在无档时被调一次）；agent 内部跑几轮自检迭代是逆向侧的实现自由，流程只认交卷时契约是绿的。
9. **三权分立——产出质量的职责划分（2026-10-14 定）**：**不错归逆向 agent**（AI 层自证：自校验+交叉验证差异进 warnings）/ **不漏归契约**（机器硬保证：schema 必填 + 显式空[拿不到=null+warnings，静默省略 key 违约] + 我方入料内部一致性校验[SQL 引用表 ⊆ source_tables∪tables、lineage target ⊆ tables.fields]）/ **真值归 provenance**（人可回查：逆向产物与线上一致性的责任在供方，我方不做新鲜度校验）。不指望一个机制包打：**双跑拦的是"新 SQL vs baseline SQL"回归，不拦"baseline vs 线上"真值**——逐字保真原则的价值是把"错"限定为机械错（漏字符/错字符，双跑/EXPLAIN 大概率炸出），杜绝理解性改写（最危险的 silent 错）。
10. **消费端倒推——契约字段的方法论（2026-10-14 定）**：契约字段 = 后续消费点需求并集（ts_baseline 组装/围栏冻结层/双跑/增量回刷/patch 定位/designer 理解/完备性自证），逐点过清单，多一个不要少一个不行；**query_sql 逐字保真是最硬必填**（fields 缺可连库回填，SQL 原文无兜底通道）。消费点→字段映射表见 12 章 §2.2。

## 四、增量还原度结论（P0 ✅ 已勘察解除）

| 增量语义位 | 可逆向性 | 来源（已验证存在于 analyzer 代码） |
|-----------|---------|----------------------------------|
| load_mode（含 merge_into） | ✅ 事实 | delete_mode 枚举 1-6，xlsx/代码仓两链都解析 |
| write_condition（MERGE ON/删除 WHERE） | ✅ 事实 | delete_condition 列 + merge_on（新增必供项） |
| 增量调度变量 | ✅ 事实 | LTS 任务 params |
| 资产级全量/增量/分区判定 | ✅ hint | detect_load_strategy |
| NOT EXISTS 自引用增量排除 | ✅ SQL 内可见 | 模式检测已有 |
| 增量字段声明 / 驱动表声明 | ❌ 语义 | 材料（where_clause 全文）交付，结论归 designer+人 |
| 历史回刷任务发现 | ❌ 现无 | 远期可选增强；第一刀人回忆 |

**结论**：原则7（回刷进第一刀）的机制依赖全部满足——增量 SQL 原文 ✅、load_mode/write_condition ✅、回刷时间范围归人。

## 八、职责边界与交卷标准（2026-10-14 定稿）

- **逆向的产出物 = baseline_v1.json，仅此一件**（可选并行：spec 草稿给 RS 段，属契约 B，不进本体系档案）。原始 DDL 文件是逆向的**事实来源**（喂 tables 段），读完即弃——不要求产出归一 DDL 文件（档案 ddl/ 由我方 ts_baseline 投影生成）。
- **建档归我方**：契约校验 → ts_baseline 组装 → etl 逐字落盘 → **原始制品拷入 archive/export/**（术加/LTS/DQ excel——patch 底本）→ ddl/ 投影。逆向不触碰档案。
- **输入形态（消费侧定义，逆向的燃料，首优一次制品全集）**：术加 excel 必给（query_sql 唯一来源，无兜底）/ LTS excel **两种情况必给**（① 增量资产——增量变量还原是回刷地基；② 预计变更触碰调度——新来源表加上游依赖、回刷加任务、DQ 加任务行——**与全量/增量无关**，全量+新来源表同样要）/ DQ excel 三态（给文件｜用户声明"资产无 DQ"[声明入档，此后永不再问]｜沉默→我方拦下问）/ DDL SQL 文件给则用、缺则我方 precheck 连库回填。
- **旅程幂等四不变量（02 章 §〇 同步）**：逆向一次（覆盖重入料除外）/ 原始制品经手一次（首优全量收齐）/ 档案演进动作封闭（ts 投影[DDL]、dq.json 投影[DQ]、patch 回存[术加·LTS]、advance——四动作之外无人手改档案）/ 用户输入两态（首优全套、常态 RS+mapping——输入集按"第几次"分类，不按"变更类型"动态决定）。

## 九、开发协议（契约演进波次，2026-10-14 定）

- **变更波次固定**：① analyzer 仓先行（schema+契约文档+fixtures+version bump——生产方权威，我方永不先改 vendor）→ ② 我方跟随（re-vendor schema+fixtures+消费端适配+契约测试绿）→ ③ 同一波内两仓各自同步内网。无契约变更的日常提交两仓完全独立（各自 commit、各自同步，零协调动作）。
- **AI 会话零交叉**：契约是唯一接口——analyzer 仓会话不需要本仓上下文，本仓会话不需要 analyzer 解析细节（语料/方言/AI 增强步骤）；人不在两会话间搬运理解。
- **工具（我方实施挂起）**：re-vendor 脚本（同机拷贝+版本戳+跑契约测试——"跟随"动作一个命令）/ 联锁检查（sync_to_team 同步前对账 vendor 版本 vs analyzer 仓 schema 版本，不一致拦截——把契约漂移发现点从内网运行时 fail-loud 提前到本地同步时）。
- 内网同步：**双源同步已上线（2026-10-14）**——analyzer skill 成品随本仓 sync_to_team 一并镜像进内部仓 .opencode/skills/（一次同步两仓就绪，见 SYNC-GUIDE ⓪节）；联动只发生在契约变更波。**部署依赖**：opt 存量首优要求逆向入口（run.py 及依赖）已随双源同步就位；缺失 = fail loud + 指引，不代跑。
