## 一～六：v3 基线条款（已实施，不变）

接口两路径 / 输入识别职责（混放不拦·.sql 归 DDL·DQ 两态）/ 产物 asset_facts.json 与四纪律 / 验收告知 / 失败语义 / 演进波次——全文见文末存档节或对接文档 docs/14。以下为**增量条款**。

## 七、产物落盘位置与交付形态（增量）

1. 产物落盘路径由调用方经 `--output` 指定——消费方固定指向**逆向暂存区**（`{ddlc}/reverse/`，消费方目录模型的一部分；**随时可删可覆盖重跑，不参与任何路由判断**）。此项你们零改动，仅告知背景。
2. **产物总是落盘**——即使检出结构级矛盾（§八）也照常产出（排查全景材料：消费方的人审要看"逆向到底解析出了什么"）。"通过与否"不体现在产物的存在性上。

## 八、自检结论三态（增量，核心）

产物交付时必须携带**自检结论**，三态：

| 结论 | 语义 | 消费方动作 |
|---|---|---|
| **通过** | 干净或仅噪音级差异 | 直接进审核对账 |
| **通过（带噪音清单）** | 存在噪音级 warnings（登记滞后类常态差异） | 对账过 → 建档，清单进闸口材料披露 |
| **待审（结构级清单）** | 存在结构级矛盾（见 §九分级） | 审核动作拦下 → 人审（换料重跑 / 显式放行） |

- 携带形态你定（产物元信息字段 / stdout 结论行 / 参数化皆可）——要求：机器可判读、三种状态可区分；
- **退出码语义不变**（0 成功/1 制品数据问题/2 参数错）——"待审"不是失败（exit 0 + 待审结论），人审放行后才算过。

## 九、warnings 严重度分级（增量）

- warnings 须带**严重度标注**，至少两级：**结构级**（指向"料可能给错/资产级对不上"：如 DDL 表与术加目标表不符、LTS 任务引用无关表、DDL 内部表冲突）与**噪音级**（平台常态差异：登记滞后等）；
- 分级口径你定（你是制品域知识的权威）；分级错误的代价消费方评估过：误升（噪音判结构级）→ 流程停一次人放行，低成本可接受；误降 → 消费方审核对账与闸口还有两道眼兜底；
- 分级驱动两个消费点：§八的待审判定 + 闸口材料的高亮（结构级置顶、噪音级折叠）。

## 十、制品间一致性交叉（增量）

同资产多类制品之间的一致性校验归你（两边料与判定知识都在你侧；差异=存量既成事实，**披露不阻断**）：

| 交叉 | 对什么 |
|---|---|
| 术加 TargetFields vs RULE SQL | 字段登记 vs 投影（已有 field_name_mismatch——确认覆盖） |
| 术加 vs DDL | 目标表存在性 + 字段集差异 |
| 术加 vs LTS | 调度任务引用的表与制品目标/源表对应性 |
| 术加 vs DQ | DQ 规则目标表与制品目标表 |
| DDL 内部 | 多 .sql 的表重复/冲突 |

- 差异逐条**可读可定位**（哪个制品哪个位置、差什么）——消费方闸口给人扫；
- 结果进 warnings（带 §九分级）。
- 〔v4 注：消费方过渡期自建了"DDL 列↔ETL 投影列"披露级对账作兜底；v2 草稿落地上列级一致性随装配天然携带后，此类交叉仍以你侧为权威，消费方兜底可收。〕

## 十一、产物形态=ts 草稿（v4 增量，核心——待波次启动）

**总要求**：产物从「物理事实包（asset_facts）」演进为「消费方 ts.json 形态的**草稿**」——草稿经消费方审核（对账消费方输入域）后**原样复制建档，零解析零变换**。任何消费方需要的变换留在消费侧=契约失败（建档幂等判据）。

### 11.1 恢复声明进本体（逆向的本职=恢复存量设计声明，不只是解析攒事实）

制品记载的**设计结果**直接回填 ts 槽位（你已解析的信息，消费方不再二次装配）：

| 制品记载 | ts 槽位 |
|---|---|
| LTS/execution_tasks 的调度方案（cron/依赖） | meta.schedule |
| DDL 的分布/分区/存储（table_props 五字段+is_distribute_key） | tables 物理属性——**必须全量映射**（v1 契约设计意图"档案 DDL 走 ts 投影无损再生"以此承载，消费方 v1 曾在此丢信息） |
| 写入类型/删除条件（write_plan） | rules load_mode / write_condition（原文另存 §11.3 增量材料） |
| SQL 口径表达式/投影/血缘 | rules.fields 三桶 |
| SQL FROM/JOIN（别名/条件） | rules.joins / source_tables（别名=SQL 实际别名——消费方 view 的别名对照直接消费） |
| **SQL 原文（query_sql）** | rules[].query_sql（**逐字保真**——v1 四纪律延续；消费方建档落 archive/etl/{rule_code}.sql=Coder 底稿/SQL 围栏基准。v2.1 增补：v2.0 漏项） |
| 读写拓扑 | rules reads / produces_for |

### 11.2 推断不冒充声明（判断位纪律）

- 制品**从未显式表达**的设计槽位留空：business_key 论证 / join_safety 依据 / 粒度完整句；
- 制品**显式记载过**的设计可回填，**带来源标记**（provenance 字段你定形态）：如 DQ 主键判重条件=显式的主键设计记录→可回填 business_key；MERGE ON=显式的写入设计→回填 write_condition（business_key 仅作其旁证**不冒充**——分布键同[无唯一性语义，仅弱旁证]）。

### 11.3 `_reverse` 审核材料段（随草稿单文件，结构定形）

| `_reverse` 字段 | 内容 | 来源（v1.4 同源） |
|---|---|---|
| `self_check` | 自检结论三态（verdict/structural_count/noise_count） | v1.4 同形 |
| `warnings[]` | severity 两级 + title/detail（**五类交叉结果并入此处**，不单列） | v1.4 同形 |
| `write_plan[]` | 写入类型原文（kind/condition_role/condition_expr/condition_columns/where）——本体 load_mode 的词典译源 | v1.4 rules[].write_plan |
| `schedule_evidence[]` | LTS 调度原文（cron 串/任务路径/依赖指向）——本体 meta.schedule/tasks 的恢复源 | v1.4 LTS 解析 |
| `evidence.business_key[]` | 判断位旁证，source 封闭集=`merge_on`（强旁证）/`dq_pk_check`（显式主键设计，可回填本体带 provenance）——**分布键不得作旁证**（无唯一性语义） | 新增 |

下划线键=非资产语义，消费方围栏/UT/切片天然忽略。**档案单文件自足**由此成立——消费方 view 从档案单文件渲染（别名/拓扑/旁证/warnings 全在档）。asset_facts 原始产物随档作出生证明的既有动作保留。

### 11.4 契约交付包与波次（已定稿）

**交付包四件套，一起 vendor**：

| 件 | 角色 |
|---|---|
| `ts_draft_v2.schema.json` | **契约必填面**（机器验：恢复槽位必填/判断位留空合法/_reverse 段/旁证封闭集）——进门验 |
| `ts-template.json`（消费方 skills/dws-design/assets/，JSONC 带注释） | **完整结构权威**——生成的目标形态全貌（人读）：meta 全段/tables 全键/rules 全键/data_flow/tasks/init 等，schema 未逐一描述的字段以此为准 |
| `ts_draft_v2.example.json` | **草稿形态参照**——恢复槽位有值+判断位留空+`_reverse` 填好的一份完整草稿样子（非生成指令） |
| `ts_sample_forward.json` | **本体全貌靶（你们点名要的）**——正向设计链路真装配产出的一份真实 ts.json（增量场景：extract×2+merge，全槽位真实有值——判断位/调度/init 增量段/审计列全在）。**对齐形态不抄值**：判断位（business_key/grain/join_safety）在草稿里按 §11.2 恢复/留空纪律处理，正向样本只演示"槽位填满时长什么样"；随消费方装配器演进同步（波次） |

- 分工：schema=进门验，template+样例+正向样本=需求形态参照（**非生成指令**——解析与装配实现全归你侧），消费链校验（围栏/UT/组装校验）=终局守——草稿最终要能被消费方全链消费；
- **你们 vendor + 指纹联锁**（方向与 v1 相反——v1 是你们权威我们 vendor）；四件随契约波次同步演进；
- 关键不变量（schema 之外）：**档案 DDL 投影无损**（tables 物理属性承载，见 11.1）；词表外 kind **禁止硬映射**（空串+待定进 warnings——沿用 v1.3 纪律）；**草稿直接产标准三桶形态**（rules.fields direct/processed/assign——v1 产物的旧形态 field_targets/field_logics 不再产）；
- v1（asset_facts）与 v2（ts 草稿）**双支持期**：消费方按产物自描述版本路由；演进走 §六波次。

### 11.5 调度映射表（LTS/execution_tasks 制品 → ts 槽位）

| 制品事实 | 落位 | 形态 |
|---|---|---|
| 调度周期/cron 表达式 | `meta.schedule.cron` + `schedule_type`（频率推断自 cron） | **恢复**（平台配置的设计结果） |
| 任务依赖指向（上游任务） | `meta.schedule.upstream_added`（依赖清单） | **恢复** |
| 依赖语义类型（同周期/时间点/上周期/宽依赖） | 不填（消费方默认宽依赖） | **推断不冒充声明**——制品只有依赖指向无语义类型，原文进 schedule_evidence 供人定 |
| 任务路径/GR 规则组编码等平台任务事实 | `tasks` 段 | **恢复**（LTS 制品有则填） |
| 以上全部原文 | `_reverse.schedule_evidence[]` | **证据随行** |
