# 07 · 制品与收尾

> 第7章定稿（v2.0）。三个第1章挂账开放项本章收口：原始制品使用方式（交付副本模式）→ patch 语义（严格 patch）→ warnings 消费方式（报告+存档）与 provenance 形态（混合）。**机制按 change type 参数化设计（原则6）：patch 引擎 = 编辑原语 × 变更声明，第一刀只实现 add_field 的映射，动作表中的其余行为为未来扩展预留的设计验证。**

---

## 一、原始制品的使用方式：交付副本模式

- patch 工具按 provenance 定位原始制品 → 产出**更新后的完整文件副本**进交付目录，附 **patch 说明**（哪个文件 / 哪个位置 / 改了什么 / 对应 change 哪条）。
- 人拿现成文件去执行（替换代码仓文件 / 导入平台 / 提交 PR）——**我们不就地改原件、不碰仓**（推生产不自主）。
- patch 说明进闸口②'交付物清单一并确认。

## 二、patch 语义：严格 patch

- **只落变更清单内的修改点；逆向发现的存量声明漂移原样保留，仅在报告提示**。
- 理由：①顺手修会把别人的历史遗留和我们的变更混进同一交付，审计必须可区分；②修漂移本身是变更，走变更清单扩充经人确认（第3章机制），不做 patch 副产品；③制品层同样满足"diff 恰好等于变更清单"——三段审计链（ts 层 / SQL 层 / 制品层）同标准贯穿。

### warnings 的消费方式（第1章挂账项①，本章收口）

**报告展示 + 存档，不参与 patch 决策**。闸口②'一屏"资产健康提示"（存在 N 处声明与实跑不一致，本次未处理），人不被要求逐条审（原则9）。

### provenance 的具体形态（第1章挂账项②，本章收口）

**混合**：路径优先（patch 按路径找原件），快照兜底（逆向消费过的源文件内容存 `_internal/`，路径不可达时用快照出副本）——patch 永不因文件挪动/换机器卡死。

## 三、patch 引擎：编辑原语 × 变更声明（可扩展设计）

**编辑原语**（小而封闭的集合）：`单元格替换 / 行追加 / 行更新 / 行删除 / 文件新增 / 文件删除`。

**每种 change_type 的制品动作 = 声明驱动的原语组合**（第一刀只实现第一行）：

| change_type | 术加 xlsx / 规则 yml | DDL 变更单 | LTS 调度 | DQ |
|-------------|---------------------|-----------|---------|-----|
| add_field（第一刀） | TargetFields 行追加 + 规则 SQL 单元格替换 | ALTER ADD COLUMN | 零变更 | RS 提了才文件新增 |
| modify_field（预留） | TargetFields 行更新 + SQL 替换 | ALTER TYPE（如需） | 零变更 | 条件更新 |
| drop_field（预留） | TargetFields 行删除 + SQL 替换 | ALTER DROP COLUMN | 零变更 | 引用清理 |
| add_source（预留） | 实体级行追加 + TargetFields 多行 + SQL 替换 | 视血缘而定 | 零变更 | 条件新增 |
| 性能重构（预留） | 规则行增删 + TargetFields 批量 + 调度可能变 | 视结构而定 | **可能变更** | 零变更或迁移 |

- **定位**：稳定标识（rule_code / 目标字段名），不做行号假设。
- **保真铁律**：只动定位点；未知列 / 未知 sheet / 格式原样保留；xlsx 新增行样式从相邻行复制；yml round-trip 保注释保顺序。
- 视图（I 视图资产）：基于原视图文本精确加列（同 SQL 围栏逻辑），CREATE OR REPLACE 随 DDL 变更单。

## 四、其余制品动作

- **DDL 变更单**：进交付（人拿去线上执行）；**全量 DDL 仅推进档案**，对外不交付。
- **回刷脚本**：进交付（INIT SQL + 时间范围）+ 随档案写回——原则7"回刷脚本必须归档"的落实。
- **调度 / DQ 条件化**：按 change type 动作表（上表），非全局规则。

## 五、收尾：闸口②' → 写回档案

闸口②'两问（第6章）+ patch 说明确认 → 流程结束 → **写回档案**（v1.7 循环链闭合）：ts_v2 + 新 SQL + 全量 DDL + 本次交付目录成为档案当前态。
