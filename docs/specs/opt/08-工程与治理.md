## 一、opt-pipe.md 剧本

```
0. 入口检查：查档案——有 → 直接用；无 → 收 baseline_v1.json（契约校验 fail loud）→ 入料建档
1. 输入校验：标注解析 → change_request + 一致性校验（02 §三清单）+ 类型风险复用（TYPE_RISK 流程）
2. designer（dws-design-opt，prompt 显式模式声明）→ ts_v2
3. 围栏（fence_check，pipe 调）→ 闸口①'（三问）
4. coder（dws-coding-opt，组内并行）→ SQL 围栏（pipe 独立跑）
5. UT：check_db → 6a 预检（ALTER 替代 CREATE）→ 6b 执行 + 输出对比 → 失败三类分流
6. 制品：DDL 变更单 + patch 副本 + patch 说明 [+回刷脚本] [+DQ]
7. 闸口②'（两问 + 健康提示一屏 + 交付清单）→ 写回档案，流程结束
```

编排者铁律原样沿用：不 author 脚本、校验失败按路由走不自动修、诊断进 `_internal/diagnose/`、闸口非交互跳过须显式声明。

## 二、档案区

- `archives/{appid}/{schema}/{资产}/{NNN_日期}/`：ts + etl SQL + ddl + change + decisions（全文本小件）——**入 git**。
- xlsx 大件不进档案（运行时产物可再生）；`10_project_deliver` 保持运行时语义（gitignore 照旧）。
- **new-pipe 配套**：交付时写档案（归档步骤/脚本）——档案路径（自建资产优化）的输入来源，第一刀一起做。

## 三、新增/改动的脚本清单（按调用方归位，同步 tool-registry）

**design-dev-shared/scripts（pipe 调）**：

## 七、实施顺序（v2.3 定：分阶段 + 评测闸门）

**背景**：新建场景仍在持续迭代，优化场景须控制对存量的冲击。影响面 = 九成纯新增 + 四个存量接触点（assemble_ts / ut_precheck·ut_execute / assemble_ddl / new-pipe 剧本归档步骤）。

**阶段一（立即启动，零存量接触）**：契约对接（vendor schema + fixture）→ assemble_ts_baseline → preprocess_opt → fence_check → sql_fence → dws-design-opt / dws-coding-opt → opt-pipe 剧本前半（入口→ts_v2→围栏）。**验收线：跑到 ts_v2 产出 + 围栏通过。**
开工首查：new-pipe preprocess 对 mapping"变更标识"新列的容忍度（未知列是否报错）。

**阶段二（启动闸门 = 新建评测能力到位）**：assemble_ts 增量模式、ut_* 扩展、assemble_ddl 优化模式、new-pipe 归档步骤、artifact_patcher、三案例全链路 + eval 优化用例。

**改动纪律（阶段二全程有效）**：
1. **加法式**——新函数 / 新参数 / 新模式；不带优化参数时现有路径逐字节同行为；
2. 每次动存量文件，732 个单测全绿 + 评测健康回归通过才算数；
3. 优化场景改动与新建场景迭代在同一文件冲突时，加法式改动可共存（不同函数/分支），禁止改写现有函数签名与行为。
