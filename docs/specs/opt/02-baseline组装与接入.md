# 02 · baseline 组装与接入

> 第2章定稿（v1.7）。核心：**唯一锚点 = 体系内资产档案**，json 只是入料；优化循环链"读档案→增量设计→ts_v2→交付写回"；流程无断点；不校验新鲜度；存量语义第一刀不补（入料路径）。

---

## 〇、档案模型（本章地基，v1.7 定）

- **唯一锚点 = 体系内资产档案**：ts + etl SQL + ddl（交付物全集）。所有资产在体系内只有一个表示，优化永远从它出发。
- **优化循环链**：读档案（baseline = 档案当前态）→ 增量设计 → ts_v2（完整结构 + change 段）→ 交付时**写回档案**（当前态推进，下次即 baseline）。
- **json 只是入料**，出场仅两时机：① **无档入料**（外部资产首次进体系）；② **有档但供方交了 json** = 声明"线上被外力改过、档案过期" → **覆盖重入料**（重建档案；会清掉档案攒的语义——第一刀无影响，将来做继承时加"结构未变位保留"）。
- **写档案只有两个动作**：json 入料 / **懒归档**（首优时从 10_project_deliver 标准产出拉档——new-pipe 不做归档步骤，v2.5 修正：不为不确定的优化预付成本）。日常有档优化**不需要 json**——资产一旦入体系，逆向退场。
- **历史 = 按次交付目录序列**（每次优化一个带序号/日期的交付目录，"档案当前态"即最新目录；ts 文件内部不含任何历史记录）。目录命名与档案持久化存放 → 第8章。

## 一、入口与流程

- **入口**：RS + 已标注 mapping +（json，仅上述两时机才出现）。缺必要项不开工。
- **优化命令第一步：按资产查档案**——有档直接用（零组装、语义全在、自建增量资产的 init 段可直接复用于回刷）；无档则必须有 json → 契约校验 → 组装建档（语义空位 + 校验豁免）→ 继续。
- **标注在上游完成**：到我们这里时优化需求点已在 mapping 里标好（变更标识列）。流程内**无断点**。
- **mapping 是业务侧交付物**：我方只发布输入格式规格（`docs/specs/mapping-format.md` 扩展"变更标识"枚举列），对齐对象是**交付方**；业务侧怎么产出（基于逆向视图加工/手写）不是我们的事，**不做跨 agent 设计**。
- **不校验新鲜度**：默认输入内容准确，真实性/时效性责任归供方（交 json 是供方表达"档案过期"的唯一通道）。我方只做格式校验 + 输入内部一致性校验。
- **逆向不进 pipe 调用**（见 01 §一调用边界）：analyzer 是 peer agent，文件交接。

## 二、我方加工链（从 json 到 designer 可开工）

```
baseline_v1.json
  → 契约校验（vendored schema：version / required keys，fail loud）
  → ts_baseline 组装（assemble_ts_baseline.py，独立脚本；ts 结构构造函数与 assemble_ts 单源共享）
      存量语义位显式空值 + 校验自动豁免（_reverse_engineered）
  → etl_baseline/{rule_code}.sql（query_sql 逐字落盘，视图规则也落）
  → baseline_view（从 baseline_v1 直接渲染，designer 读：资产概览/规则清单/load_mode/write_condition/
      源表/增量材料 where_clause/字段血缘摘要/hint（非权威）/warnings 摘要）
  → 准入检查（第一刀资产形态：单规则组、SQL 可逆向等，不满足拒收并报支持清单）
```

## 三、输入校验清单（B 段，解析标注之后）

| 校验 | 处置 |
|------|------|
| 交叉校验：标"新增"但 json 已有 → 冲突；未标但 json 没有 → 漏标提示；标识值非"新增" → 拒收"本刀不支持的变更类型" | 冲突/漏标 question 人；拒收报支持清单 |
| 双源对账：RS 优化章节字段清单 ↔ mapping 标注清单 | 对不上 question 人 |
| 实体级-属性级配对：新增字段源表引用能落到实体级 | 悬空 → 阻断人改输入 |
| 资产定位一致性：mapping 目标表 == json 资产表 | 不一致 → 阻断 |
| 回刷意向 × load_mode 一致性（全量基线声明回刷=无意义） | 提示 |
| DQ 需求引用字段存在性 | 不存在 → 阻断 |
| 新增字段命名规范（存量不审、新增按我方标准） | 违规 → 阻断 |
| 同需求内新增字段同名 | 重复 → 阻断 |
| 输入预检（连库）：完备性 / 源表字段存在性+类型 / **类型风险复用新建 TYPE_RISK 决策流程**（question + fill 脚本 + 回写） | 对齐新建 precheck 0/1/2 分级 |

校验三问模型：机械判定归脚本、语义判断归人（question）；问题三去向（人改输入 / question 人决策 / 拒收停线），**无"pipe 自动修"**。

## 四、语义结论（第2章核心分析）

| 信息 | 消费方 | 第一刀外部资产 |
|------|--------|---------------|
| 新字段业务口径 | designer/文档 | 不用专门补——RS 优化章节天然提供 |
| 新 JOIN 关联安全性 | designer 决策+校验 | 不用专门补——designer 为新关联声明 |
| 存量表主键 | UT 主键检查 | **不补**——双跑（老列逐值一致）强于主键检查；存量问题非本次引入 |
| 存量关联安全性 | 设计校验 | 不补——生产在跑即证明 |
| 存量表粒度 | 锚点校验 | 不补——豁免 |

- 兜底：某机制硬需要一条存量信息时，**按需点补**（question 人，当场补那一条），不预填全景。
- **继承/档案机制延后**：交付物归档留存（免费）；"抄答案"（下次把上次人给过的语义抄过来）等二次优化真出现再做，增量工程不返工。
