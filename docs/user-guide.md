# 设计开发段使用指南

> 你把 **mapping**（字段映射 Excel，必须）和 **RS**（需求文档，可选）交给本段，
> 拿回 **TS**（技术方案）和**四件套**（建表 DDL / ETL SQL / 调度包 / 质量检查 SQL）。
> 全程自动执行，只在关键处停下来问你。
>
> 版本：内网仓 `git log` 里最近的 `sync: design-dev-agent@{hash}` 提交 = 当前部署版本。

---

## 1. 开始：找到你的场景，抄一条命令

在 opencode 里敲对应命令（参数用分号隔开，路径写**绝对路径**）：

| 你要做什么 | 命令 |
|---|---|
| **新建**一个资产 | `/new-pipe mapping=D:\需求\xxx_mapping.xlsx; rs=D:\需求\RS_xxx.md` |
| **优化**已有资产（之前用本段交付过） | `/opt-pipe mapping=D:\需求\xxx_mapping.xlsx; rs=D:\需求\RS_xxx.md` |
| **优化**已有资产（没用本段交付过，只有制品包） | `/opt-pipe mapping=D:\需求\xxx_mapping.xlsx; artifacts=D:\存量制品目录` |
| 上次**没跑完**（中断/关窗口） | 原命令**原样重发**即可，已有产出自动重建，不会污染 |
| 不需要 RS | 把 `rs=...` 去掉即可（调度/增量/质量检查走默认值，正式交付建议带上） |

**发起前就检查两件事**：

1. **在哪个目录启动 opencode，产出就长在哪**——想让产出长在哪，就在那个目录启动（产出在 `<启动目录>\10_project_deliver\...` 下）。别在产出文件夹里面再启动。
2. mapping 别放进 `10_project_deliver\` 产出树里。

**命令里写其他话不会被执行**（防注入的刻意设计）——你的要求等流程停下来问你时说（§4）。

---

## 2. 参数速查

| 参数 | 必填 | 说明 |
|---|---|---|
| `mapping` | ✓ | mapping 文件绝对路径（优化场景=**全量** mapping，含「变更记录」页签）。资产名/schema 等自动从输入推导，不用传 |
| `rs` | | RS 文件绝对路径；不传=无 RS 模式 |
| `artifacts` | 优化 | 存量制品**目录**（xlsx 等丢一个目录，命名随意）——无档案时走这条，自动识别建档 |
| `baseline` | 优化 | 已有 ts 草稿 json 的绝对路径；与 `artifacts` 二选一 |
| `交互` | | `non-interactive`=不停等确认，跑完你后审（**需要你决策的问题依然会停**） |

漏了必填参数不会猜——直接报"缺 {键}"，补上重发。

---

## 3. 敲完命令后会发生什么（一分钟版）

```
敲命令 → ① 可能问你输入问题（类型/关联键对不上时）
       → ② 请你确认设计                ★必答
       → ③ 自动编码 + 真实库测试
       → ④ 可能问你质量问题（测试发现异常时）
       → ⑤ 请你确认交付                ★必答
       → ⑥ 生成档案，拿产物
```

两条规则贯穿全程：

- **不答不走**：需要你的判断时，流程会一直等，绝不替你选默认答案。
- **改了设计会再确认一次**：你提出修改意见后，改完的方案会重新给你确认，不会闷头改完就交付。

## 4. 你会被问到的问题（应答手册）

按出现顺序排列。带 ★ 的是必停必答，其余是条件触发（一切正常就 silently 跳过）。

### 4.1 「有些字段的类型对不上，怎么处理？」

出现时机：输入检查发现"直接复制"的字段，源和目标类型有转换风险（例：源 `varchar(20)` → 目标 `number(10,2)`）。按类型对分批问：

| 选项 | 含义 | 选完之后 |
|---|---|---|
| 转换 | 加安全转换，转不动的值置空（会被质量检查抓出来） | 继续 |
| 不加 | 原样搬，脏值可能在测试阶段报错 | 继续（风险留痕） |
| 返源端 | 是类型定得不合理 | **本次终止**，改 mapping 后重新发起 |
| 拆开逐个定 | 这批字段想分别处理 | 逐个再问 |

注意：前两种只改加工程序，**目标表结构不变**；要改结构选"返源端"。

### 4.2 「关联两边的键类型不一致」（关联键：一边 number 一边 varchar 之类）

三选：**转换** / **改关联键**（字段选错了，改 mapping 重来）/ **接受**（业务确认没问题，留痕）。会附上两侧数据的采样，帮你看内容能不能对上。

### 4.3 ★ 「设计做好了，请确认」（闸口①）

**你会看到**：设计摘要（几张表/几条规则/多少字段）、关联质量实测结论（每张表的键唯一性、有没有数据膨胀/丢失——只报事实）、完整设计文档 `ts.md`（就在产出目录，想细看就打开）。

**你确认的是**：表结构、规则划分、粒度和主键。确认后设计冻结进入编码。

| 选项 | 什么时候选 |
|---|---|
| 确认设计，进入编码 | 没问题 |
| 需要修改设计（说明哪里改） | 任何设计不满：**想拆分、想改粒度、想换关联、想改口径，都在这里直接说** |
| 源端输入问题→退 BA | 实测发现源数据脏/一对多，终止本次，BA 修完源端重新发起 |
| 放弃 | 结束，产出留现场不建档 |

两个提示：关联质量结论只是披露（不唯一≠一定是设计错，可能是开发库数据脏，由你判断）；输入资产名带 `_i`、产出表带 `_f`（前者是后者的镜像视图）——**名字差这个后缀不是错误**。

### 4.4 「测试发现数据对不上，是什么原因？」

出现时机：真实库装载成功但检查失败（主键重复/空值/行数异常）。会先给你摆证据（哪个表、哪些键重复、样例数据），请你定原因：

| 选项 | 什么时候选 | 选完之后 |
|---|---|---|
| 关联设计问题 | 关联发散了，要调整关联条件 | 改设计→**重新给你确认（回到 4.3）**→改 SQL 重测 |
| 源表数据问题→退 BA | 源端一对多/脏数据（**现实中大多数是这个**） | 终止本次，BA 修完重跑 |
| 业务粒度问题 | 业务上就是一对多，主键该多加字段 | 确认后改主键定义 |
| 编码实现不符 | 设计是对的，程序写偏了（如漏了分组） | 直接修程序重测，不再确认 |

放心：这类问题**不会被简单去重糊弄过去**（去重掩盖根因=丢数据）；另外开发库和生产数据不完全一致，结论结合数据现状判断。

### 4.5 「质量检查报了告警，怎么处理？」

出现时机：质量检查 SQL 查出了违规行（**0 行=通过，非 0 行=告警**，附违规样例）。告警不会自动消，攒到交付确认（4.6）一次判完，每条三选：

| 选项 | 什么时候选 |
|---|---|
| SQL 写错了 | 检查逻辑翻译错了（如方向写反）→ 修该条 |
| 检查不合理 | 阈值/口径定得不对 → **你定新口径**（照译）或取消该条 |
| 数据真脏，豁免 | 检查保留但不再告警（标记豁免+理由留痕） |

### 4.6 ★ 「全部完成，请确认交付」（闸口②）

**你会看到**：测试结果汇总、质量检查设计与执行结果同屏（4.5 的裁决在这里做）、产出文件清单、制品完整度报告。

| 选项 | 含义 |
|---|---|
| 确认，结束 | 制品以占位符形态出厂，**生成资产档案**，完成 |
| 确认，补充项目信息 | 有些平台信息流程不掌握（项目编码/子项目中文名/规则组编码/调度依赖任务号），逐项问你要（每项可"跳过"），补完重新生成制品再建档 |
| 确认，内网完善 | （内网部署且回填工具就位时才出现）你补两项信息，自动回填出完整包 |
| 修改 | 说明哪里改：程序问题直接修；设计问题改完**回到 4.3 再确认** |
| 放弃 | 结束且不建档 |

> 制品里的占位符/空值只有三个来源：**你提供、工具回填、保持占位**——永远不会被编造填充。看到占位符不是 bug，是等你补。

### 4.7 优化场景专属的三个问题

| 问题 | 你看到什么 | 怎么答 |
|---|---|---|
| ★ 变更方案确认（闸口①'） | 逐字段落位表："字段 X 挂规则 R，新关联表 T，中间表不动"；最多四问：落位/历史数据要不要重刷/建议追加的变更/带病确认（输入有新披露问题时才问） | 确认 / 修改（说明哪里改）/ 放弃；发现过输入问题的场景会有"退 BA"选项 |
| 老数据回归失败/新列全空 | 先给你定位证据，再问原因 | 设计问题（你定改法，改完**重回闸口①'确认**）/ 源数据问题（找数据方处理） |
| ★ 交付确认（闸口②'） | 新列空值率、与预期差异样例、交付物清单 | 确认后档案推进到新版本；**确认前档案零改动——中途放弃无任何影响** |

优化场景的输入检查（4.1/4.2 同款）另有一份**输入体检报告**（`build\_internal\input_health_report.md`）：必须修的/待决策的/可带病继续的，一次收全——改输入一轮全改完，不用挤牙膏。

### 低频问题速查

| 你遇到的 | 怎么办 |
|---|---|
| 检查直接阻断，说缺 schema/字段对不上 | 不是选择题：按报告指的位置**改 mapping/RS 文件**，重新发起 |
| 报数值溢出/超长（overflow / too long） | 二选一：输入问题→BA 改模型；过程取舍→你拍板显式置空或截断 |
| 没配数据库 | 不停等——自动跳过测试直达交付确认，报告会告知。想跑测试找部署管理员配库 |
| 优化场景报入料问题（缺料/串包/新鲜度冲突） | 报错自带处理指引：补料 / 核对资产与料 / 三选一 |

## 5. 想提自己的要求

**流程停下来问你的时候，就是你的发言窗口**——给的选项只是常用答案，不是边界，直接说你的要求即可。例：

> 确认设计时看到一条规则产 300 个字段太肥 → 直接说"把这条规则拆成两级" → 按你的要求重做 → 改完**重新给你确认**。

| 时机 | 适合提 |
|---|---|
| 设计确认（4.3） | 拆分/合并、改粒度、换关联、改口径、调表结构 |
| 交付确认（4.6） | 对程序或设计的任何不满 |
| 质量问答（4.4/4.5） | 你的业务口径、阈值判断 |
| 跑完之后（后审） | 恢复原对话说明问题，或改输入重新发起 |

## 6. 出问题了（对照表）

| 现象 | 原因 | 你做什么 |
|---|---|---|
| 第一步就停，报环境/版本问题 | 部署问题 | 按报告里的指引找部署管理员，或更新内网仓重试 |
| 报"缺 {键}" | 命令参数写漏 | 检查 `mapping=` 拼写与路径，补全重发 |
| 连不上库/权限/源表不存在 | 环境 | 报告自带指引，找 DBA/管理员 |
| 跑到一半没动静 | 大概率在等你回答 | 看对话里的问题；真卡死就原命令重发（幂等） |
| 找不到产出 | 启动目录不对 | 回看 §1——产出长在启动目录下 |
| SQL 报错、测试失败之类 | **不用你管** | 程序类错误自动修复重试（每处最多 3 轮），修不好会带着原因来问你 |

## 7. 拿到了什么，接下来做什么

```
<启动目录>\10_project_deliver\{appid}\{schema}\{资产名}\ddlc_design_dev\
├── build\               ← 本次交付现场（拿这一个目录就能部署）
│   ├── ts.md               设计文档（人读）
│   ├── ddl\ etl\ dq\       建表 DDL / 每规则 SQL / 质量检查 SQL
│   ├── export\             术加平台包 + 调度包（xlsx）
│   ├── ut_report.md        测试报告
│   └── _internal\          过程产物，忽略
└── archive\             ← 资产档案（交付确认后生成；git 合入对象；下次优化的基线）
```

接下来的动作都是你来做：①细看 ts.md 与测试报告；②**上线**（执行 DDL、配置 ETL 与调度、导入平台包——**推生产永远是人的动作**）；③把 `archive\` 按你的节奏提交 git；④制品里的占位符在平台上补全，完整包建议存回档案目录。

## 8. 常见问题

**没有 RS 能跑吗？** 能，mapping 独立驱动；调度/增量/质量检查走默认值。正式交付建议带 RS。

**没有数据库能跑吗？** 能跑到交付确认（设计/编码/制品全产出），跳过测试——等于没有执行验证，风险由你在交付确认时承担。

**non-interactive 是什么？** 无人值守批产：两次确认不停等，跑完你后审；但需要你决策的问题（4.1/4.4 等）依然会停下来等。

**LTS 调度包里的项目名、任务组是怎么定的？** 不是从你的输入来的——来自部署配置文件，按目标库的 schema 查表：不同 schema 可配不同值，没单独配的用全局默认；初始化任务、质量检查任务还可挂到与日常任务不同的项目/任务组。这些值在**确认设计时就已定格**。交付确认时看到"待配置"，说明配置文件没配到这项——找部署管理员补配置后重新生成制品，或在确认交付时人工提供（同族的规则组编码 `GR_xxx` 也是占位符，内网取码后替换）。

**中途想改需求？** 还没确认设计→在停等点直接说；已确认→等最近停等点提，或终止后改输入重新发起（输入变了流程自动从头走）。

**怎么知道跑到哪了？** 看对话（每步都有进度）；产出文件也是信号（ts.md 出现=设计完成，ut_report.md 出现=测试完成）。

**要花多久？** 中小资产几十分钟（测试灌数与库性能相关）；你的参与集中在两三次问答，每次几分钟。
